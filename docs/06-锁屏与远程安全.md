# DSH Link · 锁屏与远程安全

> 需求 9：PC 端插件增加锁屏功能。
> 本文定义锁屏**做什么、能做到什么、做不到什么**。最后一段比前面重要——一个安全功能如果说不清边界，它带来的就只有虚假的安全感。

---

## 0. 一句话结论

锁屏由**三个互不替代的强制点**组成：界面锁（挡人）、远程锁（挡设备）、危险动作闸（挡接口）。三者都能完整实现的部分，我们全做；不能完整实现的部分，本文明确标注，并且**在产品文案里也不装作做到了**。

`dsh-startup-moss` 已经证明了「访问门口令」这条路可行（`lib/gate.js` 288 行 + `lib/gate.css` 门禁壳）。我们不是从零开始，而是把它的**一次性门禁**升级为**持续状态**。

---

## 0.1 锁的是什么：dsh 的操作能力，不是操作系统的登录屏

这个词必须先在开头钉死，因为「锁屏」在 PC 语境下默认指操作系统锁屏，而我们要做的是完全不同的东西。**做错这一层理解，后面每一条实现都会歪。**

| | 操作系统锁屏 | 本插件的锁屏 |
|---|---|---|
| 锁的对象 | 整台电脑的用户会话 | **dsh 这一个应用的操作能力** |
| 触发者 | Windows / macOS（`Win+L`、合盖、屏保） | dsh 自身（空闲超时 / 手动 `⌘⇧L` / 手机请求） |
| 锁住之后 | 谁都进不来，dsh 也跟着被挡住 | dsh 窗口还在、进程还在、agent 还在跑，但**任何操作都被拒绝** |
| 谁来解 | 系统账号密码 / 生物识别 | dsh 自己的密码 / 解锁票据 / PC 端确认 |
| 我们该不该做 | **不该做**（见下） | 本文的全部内容 |

所以「dsh 上锁了」的准确含义是四句话：

1. **PC 上打开 dsh 看到的是锁屏界面**，不是会话列表。不是盖一层半透明遮罩，是把内容从 DOM 里移除（§4.1）。
2. **即使绕过界面，也发不出指令**：每一个 RPC 调用都要过网关的 `guardLock`，锁死态下除 4 个豁免方法外全拒。
3. **dsh 进程没停**，正在跑的 agent 任务继续跑完。锁的是"人能不能操作"，不是"机器能不能干活"——这两件事绑在一起会让锁屏变成一个会毁掉长任务的危险按钮。
4. **手机端进入只读观察**：能看会话、看执行过程的面包屑、看改了哪几个文件，但发指令、改文件、上传一律被拒（分级见 §5 与 07 §5）。

**为什么不去锁操作系统**：

- 需要系统权限（macOS 的辅助功能授权、Windows 的 Session API），一个 dsh 插件去申请这些是明确的权限放大；
- 用户预期冲突：他要的是"别让人动我的 agent"，不是"把我整台电脑锁上"；
- 不可移植：三平台三套 API，而这条路径的收益是 0 —— 想锁系统的人按 `Win+L` 就行了。

这也决定了一条边界：**本插件不碰 OS 的锁屏状态**。dsh 锁着的时候系统可以是不锁的，系统锁着的时候 dsh 也可以是未锁的（回来后直接可用）。两者互不感知。

## 1. 场景：为什么 dsh 需要锁屏

dsh 是"能执行代码的 agent"。它的界面本身就等于一个 shell。官方目前没有任何锁定能力（全仓 `screen.?lock|lockScreen|idleTimeout|autoLock` 零命中），意味着：

| 场景 | 没有锁屏时 | 有锁屏时 |
|---|---|---|
| 你去开会，屏幕亮着，同事过来问事情 | 他能看到你的会话、你的代码、你的密钥讨论 | 他看到一块终端锁屏 |
| 你在咖啡厅打开 dsh 查东西，起身去买咖啡 | 笔记本合盖前的那 40 秒，任何人都能发指令 | 30 秒无操作自动锁 |
| 手机连着家里 PC，地铁上手机被拿走 | 拿到手机的人能直接发指令 | 需密码 / 生物识别，且 PC 端可远程踢掉 |
| 你把 dsh 挂在小主机上给团队用 | 谁打开浏览器谁就是 owner | 锁屏 + 密码，解锁记录可审计 |

第 4 条是这次需求真正的来源：**DSH Link 让 dsh 从"我桌上的工具"变成"一台我可以远程操作的机器"，那么这台机器就必须有一把锁。**

## 2. 与 moss 门口令的区别（不要重复造）

| | moss 门口令 | DSH Link 锁屏 |
|---|---|---|
| 触发 | 页面加载后延迟一次 | 页面加载 + 空闲超时 + 手动 + 远程请求 |
| 生命周期 | 解锁即永久（当前会话） | 一直存在，可反复进入 |
| 强度 | 界面门禁（自己声明） | 界面锁 + 远程强制 + 动作闸 |
| 存储 | `sessionStorage` / `localStorage` 一个 '1' | 服务端签发的**解锁票据**（含过期与作用域） |
| 失败处理 | 401 + 剩余次数 / 429 | 同上 + 递增延迟 + 可选锁定通知 |
| 远程设备 | 不涉及 | 由 dsh-link 网关强制执行 |

**可以复用的三样东西**（不重写）：

1. `scrypt(salt, password)` 的服务端校验方式（浏览器永不接触 salt/hash）——这是对的，必须沿用。
2. `moss-gate-shake` 的抖动曲线（`lib/gate.css:58-68`），失败反馈用它，不要另设计。
3. 焦点陷阱与 `html.lock { overflow:hidden }` 的写法。

**必须改的一样**：moss 把解锁态存在 `sessionStorage` 里一个裸 `'1'`。这东西一改就开。我们的解锁票据由服务端签发并带 HMAC，客户端改不动。

## 3. 威胁模型：先把对手列清楚

锁屏的价值完全取决于它挡谁。列出四类，逐条给结论。

| # | 对手 | 能力 | 是否被挡 | 靠哪一层 |
|---|---|---|---|---|
| T1 | **路过的人** | 看屏幕、动鼠标键盘 | ✅ 完全挡住 | L1 界面锁 |
| T2 | **拿到你手机的人** | 有已配对的 App、可能知道锁屏密码 | ✅ 挡住（除非知道密码） | L2 远程锁 + L3 动作闸 |
| T3 | **会用开发者工具的人，且已坐在你电脑前** | 能开 DevTools 删掉锁屏 DOM | ⚠️ **部分挡住**：能看见内容（已被 DOM 移除，见 §4.1），能发指令（本机凭据未被吊销） | L1 只能提高门槛 |
| T4 | **能访问你机器上 dsh 端口的外部进程** | 直接 HTTP 打 `/api` | ❌ 挡不住（无 cookie 时本来就被 401；有 cookie 时本插件无服务端钩子） | 无 |

T3 / T4 挡不住的原因是一个**具体的技术事实**，不是没做好：

> dsh 的接口授权链只对**非 owner** principal 开放钩子（`ctx.remoteAccess.decide`）。Gateway README 第 33 行明确写着：*"An owner call is dispatched without resource resolution or a decision."* 而本机浏览器共享的就是 owner peer。
>
> 想在本机 owner 的调用链上插一个"锁定时拒绝"，需要 `ctx.connection.rpc.intercept('/api', …)`。但 `/api` 这个 channel **只允许一个 interceptor**（`rpc-host.ts:293-295` 抛 `shared RPC channel "/api" already has an interceptor`），而 Gateway 的 Host 入口已经占用了它。
>
> 同理 `connection.requestRejection()` 是**只读查询**（`requestRejection(request): 401 | 403 | undefined`，`rpc-host.ts:123`），不是可注册的钩子，插件无法在里面加判断。

**这条要写进产品文案**：设置页锁屏开关下面那句说明就是「锁屏挡住的是人，不是进程」。moss 的做法是"诚实声明"，我们照做，而且写得更具体。

### 3.1 T4 的一个缓解（可选，默认关）

如果用户的 dsh 只通过 DSH Link 访问（不直接用浏览器打开 3080 端口），可以把 dsh 的 `host` 保持 `127.0.0.1`，只暴露我们的网关端口。这时 T4 的攻击面被压到"本机进程"——而本机进程本来就能读你的文件，加锁没有意义。

所以正确的表述是：**T4 不在锁屏的防护范围内，它属于操作系统账号安全的范围。**

## 4. 三层强制点

### 4.1 L1 界面锁（客户端半）

**目标**：人在旁边时，看不到内容、点不到任何东西。

实现要点（每一条都对应一个具体的坑）：

| 要求 | 做法 | 为什么不能省 |
|---|---|---|
| 覆盖全屏 | `position:fixed; inset:0; z-index:2147483002`（沿用 moss 的门禁层级） | 低于这个值会被某些浮层盖住 |
| 内容**移除**而非遮挡 | 锁定时给 app 根节点加 `data-locked`，CSS `visibility:hidden` + 锁层独立挂在 `documentElement` 下；同时清空 `#root` 的 `innerText` 缓存？——不，改为 `display:none` | 只做半透明遮罩，按 F12 就能看到下面的 DOM；`display:none` 至少让"顺手看"失效 |
| 焦点陷阱 | `keydown` 拦截 `Tab` / `Shift+Tab`，强制焦点回输入框 | 否则 Tab 会跑到隐藏的按钮上，回车就触发了 |
| 禁用快捷键 | 捕获阶段拦截 `keydown`，除解锁外全部 `preventDefault` | dsh 有大量快捷键（`⌘K`、`⌘P`），必须挡 |
| 禁用右键与选择 | `contextmenu` / `selectstart` / `dragstart` 全部阻止 | 防止"选中复制"残留 |
| 阻止滚动穿透 | `html.locked { overflow:hidden; overscroll-behavior:none }` | 沿用 moss `splash.css:6-11` |
| 断网不误解锁 | 解锁**必须**打到服务端 `POST /dsh-link/lock/unlock`，本地不做任何密码比较 | 浏览器里永远不出现 hash |
| 屏保/失焦也锁 | 可选：`blur` 事件 + 5 秒宽限 | 有人用 Alt+Tab 切走，回来时应该已锁 |

**一个反直觉的取舍**：锁定时**不暂停**正在跑的 agent。理由：dsh 的任务可能跑 20 分钟，锁屏暂停会让"锁屏"变成"中断"。锁屏只锁界面，不锁进程。这一点必须在设置页写明，否则用户会以为锁屏 = 暂停。

### 4.2 L2 远程锁（网关半，**唯一能真正强制的层**）

DSH Link 的所有远程流量都经过我们自己的 WSS 网关（`02-技术方案.md` §3）。因此在这一层，锁是**硬约束**：

```ts
// plugin/src/gateway/guard.ts —— 锁定态的唯一执行点
// 注意这里**没有**一份自己的豁免名单：名单在 protocol 的 METHOD_POLICY 里。
// 手写第二份就一定会在加方法时漂移（protocol 的测试里专门有一条守这个：
// "每个方法都有策略，新增方法忘了配会在这里挂"）。
import { lockRejection, RpcError, type LockState, type Method } from '@dsh-link/protocol'

export function guardLock(lock: LockState, method: Method): void {
  const verdict = lockRejection(lock, method)   // undefined = 放行
  if (verdict === undefined) return

  if (verdict === 'locked') {
    throw new RpcError('lock/locked', '主机已锁定', {
      since: lock.since, reason: lock.reason, attemptsLeft: lock.attemptsLeft,
    })
  }
  throw new RpcError('lock/readonly', '主机处于只读状态，请先解锁', { since: lock.since })
}
```

豁免名单只有 **4 个**方法，且都只读或只作用于锁本身：
`device.info`（锁定时也要能报设备名，否则 App 只能显示"离线"）、
`lock.status`、`lock.unlock`、`lock.request`。

> 早先这里写的是 `new Set(['lock.status','lock.unlock','lock.requestUnlock','ping'])`——
> 三个名字里两个不存在（`lock.request` 才对，`ping` 从来不是 RPC），
> 还漏了 `device.info`。照抄那段代码，锁定时 App 连设备名都读不到。**这是"文档即代码"最典型的坑。**

配套的三条：

1. **解锁票据**：`lock.unlock` 成功后返回 `ticket`（HMAC(deviceId ‖ expiry)），后续帧带上；`ticket` 有效期 12h，或"本次连接"。设备断开即失效。
2. **锁定即广播**：`lock.changed` 事件推给所有在线设备，App 立刻切到锁屏 UI（不用轮询）。
3. **锁定即降权**：锁定会把所有已连接设备的角色临时降到 `viewer`（见 `02-技术方案.md` §4.3 的角色矩阵），解锁后恢复。这样即使有人绕过了 App 的 UI 直接发包，也只能读。

**这一层是干净的**，因为网关是我们写的。引用需求里第 2 条"支持密码访问，安全机制"，主要靠它。

### 4.3 L3 危险动作闸（网关半 + 客户端半）

有些操作"看到"和"能做"是两件事。锁定期间，以下动作**即使 viewer 也不允许**，必须在解锁后重新确认：

| 动作 | 原因 |
|---|---|
| `plugin.install` / `plugin.remove` | 远程 RCE |
| `files.write` / `files.upload` | 写文件到工作区 |
| `terminal.create` | 直接拿 shell |
| `session.prompt` | 让 agent 执行指令 |
| `device.revoke` | 改安全配置 |

实现位置：网关的路由白名单表里加 `lockTier: 'unlocked'` 标记（见 `02-技术方案.md` §3.3 的方法白名单表），锁定态一律拒绝。

> 为什么 L3 和 L2 分开写：L2 是"锁定即拒绝一切（除豁免）"，L3 是"**部分解锁**状态下的分级"。解锁后如果 8 小时无操作，会进入 `soft-locked`（只读）状态——这时 L2 不生效（没全锁），但 L3 生效。这是"半锁"的语义。

## 5. 状态机

```
          ┌──────────────────────────────────────────┐
          │                                          │
          ▼                                          │
      [unlocked] ──idle 超时──► [locked] ──密码/生物──┘
          │  ▲                    │
          │  └──解票刷新──────────┘
          │                       │ 8h 无操作（远程）
    手动锁│                       ▼
          │                  [soft-locked]
          └───────────────────────┘
                 解锁（只读→可写）
```

| 状态 | 本机 UI | 远程可读 | 远程可写 | 可装插件 |
|---|---|---|---|---|
| `unlocked` | 正常 | ✅ | 按角色 | 按角色 |
| `soft-locked` | 正常（顶部一条黄条：「已进入只读，点击解锁」） | ✅ | ❌ | ❌ |
| `locked` | 锁屏层 | ❌（仅 4 个豁免方法：`device.info` / `lock.status` / `lock.unlock` / `lock.request`） | ❌ | ❌ |

`soft-locked` 是本设计里唯一"新造"的概念，它的价值：**人离开了但任务还在跑**。这时候你可能只想用手机看一眼进度，不想每次都输密码。所以规则是：**只读不要密码，动手要密码。**

这条规则比"全锁"更好用，也更安全——因为人在"只想看一眼"时被强制输密码，就一定会去把超时调成 8 小时。

## 6. 解锁方式

按强度与便利排序，**可叠加**：

| 方式 | 实现 | 强度 | 默认 |
|---|---|---|---|
| **密码** | 服务端 `scrypt(salt, pass)` 比对；`salt`/`hash` 只存在宿主配置里 | 中 | ✅ 必开 |
| **平台生物识别** | WebAuthn `navigator.credentials.get({ publicKey })`，`authenticatorAttachment: 'platform'`（Touch ID / Windows Hello） | 高（能挡 T3 的一部分，因为需要物理在场） | ✅ 可选开 |
| **配对设备直解** | 已配对设备 + 设备级密钥（`02-技术方案.md` §4.1）直接解锁 | 中 | ❌ 默认关（手机丢了就是灾难） |
| **远程解锁请求** | App 点"请求解锁" → PC 弹窗（需人在 PC 前点确认） | 高 | ✅ 开 |
| **恢复码** | 首次设置锁屏时生成 8 组 4 字短语，打印/抄下 | 兜底 | ✅ 强制展示一次 |

**密码的存储**：

```jsonc
// ~/.dsh/dsh-link/config.json（权限 0600）
{
  "lock": {
    "enabled": true,
    "idleMinutes": 10,          // 0 = 只手动锁
    "softLockHours": 8,          // 0 = 不进入只读
    "password": { "algo": "scrypt", "salt": "…", "hash": "…", "N": 16384, "r": 8, "p": 1 },
    "webauthn": [{ "id": "…", "label": "MacBook Touch ID", "addedAt": "…" }],
    "maxAttempts": 5,
    "windowMinutes": 5,
    "allowDeviceUnlock": false,
    "notifyOnFail": true
  }
}
```

**限速**必须服务端做（客户端做等于没做）：同一来源 5 次 / 5 分钟，超限返回 429 并**指数退避**（第 2 轮起 15 分钟）。沿用 moss 的语义（401 带剩余次数、429 带解锁时间），因为它的交互已经验证过。

## 7. 空闲检测：怎么做才不费电

不用 `mousemove` 累加。规则：

```
活动事件（去抖 1s，只在"从未活动→活动"时刷新）：
  pointerdown / keydown / wheel / touchstart / visibilitychange(visible)
不刷新活动时间：
  pointermove / scroll     ← 鼠标划过不算"在用"
```

- 计时用 `setTimeout` 单次链，不用 `setInterval`：每次活动 `clearTimeout` + 重新 `setTimeout(idleMs)`。
- 页面隐藏（`visibilitychange → hidden`）时：**立即启动"宽限计时"**（默认 5 分钟），因为人已经离开。
- 唤醒（`visible`）时：如果宽限期已过，直接进 `locked`，不等用户操作。
- 客户端半与宿主半各算一份，**以宿主为准**（客户端可能被挂起，宿主不会）。客户端每 60s 上报一次 `lastActiveAt`，宿主取两边的最大值。

**为什么以宿主为准**：笔记本合盖后渲染进程会被节流甚至挂起，`setTimeout` 会失准；宿主进程的计时还准。

## 8. 与手机的联动（这是"多机"场景下的真正价值）

| 事件 | PC | 手机 |
|---|---|---|
| PC 空闲自动锁 | 进入锁屏层，皮肤切到 550W | 设备卡状态变「已锁定」，推送一条静默通知（不响） |
| 手机请求解锁 | 右下角弹出终端风小窗：「HOST-01 请求解锁 · 来自 iPhone 15 · [批准] [拒绝]」，30s 超时自动拒绝 | 显示倒计时环 |
| 手机输密码解锁 | 不弹窗，直接校验 | 成功后 App 侧切回正常态 |
| 连续 5 次失败 | 锁屏框抖动 + 记录一条审计 | 提示「已锁定，请稍后或到电脑前解锁」 |
| PC 端手动踢掉该手机 | 该设备立刻断连，且需重新配对 | 设备消失，会话中断，提示「已被主机移除」 |

**一个必须做的细节**：`lock.status` 是**豁免方法**，所以手机在锁定时仍能读到 `{ locked: true, since, reason }`。App 首页因此可以诚实地显示"这台机器锁着"而不是"离线"——这两个状态混淆是远程工具最常见的体验缺陷。

## 9. 视觉规格（550W 锁屏）

沿用 `05-视觉与动效-MOSS.md` 的终端框，**只是内容不同**。

```
┌────────────────────────────────────────┐
│ ●  DSH-LINK / HOST-01        LOCKED    │  顶栏，右侧 550W 红字
├────────────────────────────────────────┤
│                                        │
│            ▲ 徽标（呼吸）               │  48×48，环形，青绿→红
│                                        │
│         SESSION SUSPENDED              │  13px / .18em / t3
│                                        │
│  ┌──────────────────────────────────┐  │
│  │ ●●●●●●●●                      👁 │  │  密码框，等宽，dots 逐位点亮
│  └──────────────────────────────────┘  │
│                                        │
│  [      解  锁      ]  [ 请求远程确认 ] │
│                                        │
│  IDLE 10:24 · 3 个任务在后台继续        │  11px t3，真实信息
└────────────────────────────────────────┘
```

细节：

- **密码框逐位点亮**：每输入一位，8 个 `●` 里对应位置从 `--t3` 变 `--acc` 并 60ms 缩放回弹。这一处是本屏唯一允许的"炫技"，因为它是**唯一需要用户操作**的地方。
- **徽标呼吸**：2.4s 周期，`box-shadow` 半径 6→14px。不做旋转——旋转会让人以为在加载。
- **失败抖动**：`moss-gate-shake` 原曲线，380ms，六段位移。
- **第 3 次失败后**：下方出现一行 `ATTEMPT 3 / 5`，等宽，`--warn` 色。**不弹 toast**，锁屏上弹 toast 是把自己盖住。
- **"3 个任务在后台继续"**：真实数据。它解决用户最大的疑虑——"我锁了，任务是不是停了？"

## 10. 逃生口（锁屏最怕把主人锁在外面）

moss 有四层守卫 + 五条逃生口（README §安全启动与逃生口）。我们的对应设计：

| 情况 | 逃生方式 |
|---|---|
| 忘记密码 | ① 用恢复码 ② 在 PC 上编辑 `~/.dsh/dsh-link/config.json` 把 `lock.enabled` 改 `false` ③ 删除 `lock.password` 字段（视为未设置，自动关闭） |
| 插件本身坏了（锁屏层崩了，页面白屏） | 客户端半有 8 秒看门狗：锁层脚本抛错时自动摘掉遮罩（沿用 moss 的兜底）。**宁可漏锁，不可白屏** |
| 密码正确但解锁接口 500 | 密码框下方出现「服务异常」+「以只读方式进入」按钮（只读 = `soft-locked`，可看不能动） |
| 锁屏导致无法远程操作，人又不在 PC 前 | 恢复码；或重启 dsh 后 90 秒内有一个"紧急窗口"（`lock.graceAfterBoot`，默认 90s，只允许本机回环访问） |
| 设置了锁屏但没设密码 | 启动时检测到 → 强制走一次设置向导，**不允许直接开启** |
| 插件被卸载 | 无锁。这是设计上的正确行为（卸载插件 = 放弃这把锁），README 要写明 |

**门被我锁上，钥匙必须在我手里，而且我得能砸门。**这三条缺一条，安全功能就会变成运维事故。

## 11. 审计

锁屏是唯一会产生"值得留痕"的事件的地方。`03-产品设计.md` 里提到全生态都没有审计，这里至少做最小集：

追加写 `~/.dsh/dsh-link/lock-audit.jsonl`：

```jsonl
{"t":"2026-10-23T06:40:11Z","ev":"lock","reason":"idle","idleMs":600000}
{"t":"…","ev":"unlock.fail","from":"owner","attempt":2,"ip":"127.0.0.1"}
{"t":"…","ev":"unlock.ok","from":"device","deviceId":"dev_a1b2","label":"iPhone 15"}
{"t":"…","ev":"remote.request","deviceId":"dev_a1b2","result":"timeout"}
```

规则：**只追加、不删除、不记录密码或票据**。UI 上在设置页展示最近 20 条，手机端可看。不做日志轮转（体积极小：一次锁屏约 120 字节）。

## 12. 实现落点

```
plugin/
├── src/
│   ├── index.ts          # 插件入口 + 本机 HTTP 面（makeHttpHandler）：
│   │                     #   GET/POST /dsh-link/lock · POST /lock/unlock · POST /lock/request
│   ├── lock/
│   │   ├── index.ts      # 状态机：空闲 / 半锁 / 锁定 / 限速 / 远程请求 / 广播
│   │   ├── password.ts   # scrypt + 滑动窗口限速（AttemptLimiter）
│   │   ├── ticket.ts     # HMAC 解锁票据（绑定 deviceId，进程级密钥）
│   │   └── audit.ts      # 追加写 JSONL（0600，串行化，永不记密码）
│   └── gateway/
│       ├── guard.ts      # L2 + L3 的唯一执行点（本文 §4.2 / §4.3）
│       ├── router.ts     # 方法表 + 角色校验
│       └── server.ts     # WSS 连接、心跳、广播
├── client/
│   └── lock-ui.js        # L1 界面锁（覆盖层 + 焦点陷阱 + 逐位点亮 + 8s 看门狗）
└── tests/
    └── lock.test.mjs     # 10 项：无密码不锁 / 票据作用域 / 限速 / 远程请求 / 持久化
```

**未实现的部分（P1，标注在这里以免被误认为已完成）**：

| 项 | 计划位置 | 说明 |
|---|---|---|
| WebAuthn 生物识别 | `lock/webauthn.ts` | 依赖 `navigator.credentials`，需要真机验证 |
| SSE 推送 | 替换 1s 轮询 | 现在客户端半每秒 `GET /dsh-link/lock`，本机回环成本可忽略 |
| 设备认证握手 | `gateway/server.ts` | 目前按"未配对 viewer"处理，`conn.authenticated` 从不置真。**且认证检查排在锁豁免之后**，所以未认证连接连 `device.info` / `pair.*` 都调不到——配对流程走不通，不只是"权限收紧"。见 `09` §5.3 |

宿主半向网关暴露的接口只有一个：

```ts
export interface LockState {
  readonly locked: boolean
  readonly soft: boolean
  readonly since?: number
  readonly reason?: 'idle' | 'manual' | 'remote' | 'boot'
  readonly failedAttempts: number
}
```

网关只读它，不读配置——**锁的判定权在宿主半一处**，避免两处状态不同步（这是同类插件最常见的 bug）。

## 13. 测试矩阵

| # | 用例 | 期望 |
|---|---|---|
| 1 | 空闲 10 分钟 | 进入 `locked`，UI 切 550W |
| 2 | 锁定时刷新页面 | 刷新后仍是锁定态（服务端票据不在，客户端不能自解锁） |
| 3 | 锁定时用另一台设备连接 | 除 4 个豁免方法（`device.info` / `lock.status` / `lock.unlock` / `lock.request`）外全部 `lock/locked` |
| 4 | 锁定时发 `plugin.install` | 被 L3 拒绝，错误码 `lock/locked`，attempt 不增加 |
| 5 | 错误密码 5 次 | 第 5 次后 `429` + 退避 15 分钟 |
| 6 | 正确密码 | 返回 ticket，设备角色恢复，广播 `lock.changed` |
| 7 | 拔网线后解锁 | 报错「需要连接主机」，**不本地放行** |
| 8 | 锁屏脚本抛错 | 8s 看门狗摘掉遮罩，页面可用（宁可漏锁） |
| 9 | 手动删 config 里的 password | 重启后锁屏关闭 |
| 10 | 生物识别 + 密码同时配 | 两者都能解，生物识别优先展示 |
| 11 | 8 小时无操作（远程） | 进 `soft-locked`，可读不可写 |
| 12 | 恢复码 | 一次性有效，用后作废并提示重新生成 |
