# DSH Link · 可行性分析

> 目标：为「一套 dsh 宿主插件 + 一个 uni-app 移动端」做可行性判定。
> 结论先行，再逐条拆解证据、风险和绕行方案。
>
> 参考对象：Qoder Mobile（远程控制）、WorkBuddy（多端协同）；技术参照 `dsh-mobile` 等 5 个已落地插件。

---

## 0. 一句话结论

**可行，且比想象中容易——因为 dsh 已经把「远程调用」做成了一等公民；真正难的不是技术，而是四件产品级的事：配对要足够短、多机要足够清楚、上传要绕开只读约束、装插件要足够安全。**

技术上没有不可逾越的墙，但有 **5 个硬约束**必须在架构阶段绕开，绕不开就会在 M3 推倒重来：

| # | 硬约束 | 证据 | 绕行方案 |
|---|---|---|---|
| C1 | dsh 远程文件面**只读**，不能写工作区 | `api/workspace-files/README.md`：*"The service exposes no mutation operation."*；`src/index.ts:233-340` 只有 `read/readBytes/stat/list/changes` | 插件自建上传通道，落盘走宿主 fs + 工作区根校验 |
| C2 | dsh 的 `connection` 鉴权是**进程级 token + Cookie**，没有账号体系 | 前序分析：launch token → 30 天签名 Cookie，无登录/登出 | 插件独立网关，自建设备身份；**不碰** `connection` |
| C3 | 客户端模块 `platform` **硬编码只认 `'web'`** | `client/modules/src/index.ts:862` 附近 | 不依赖 client 半，原生 App 直连插件网关 |
| C4 | 官方**无推送通道**、无 `PrincipalMap` 非 owner | RBAC 生产只有 `owner`；无通知服务 | 自建 APNs/FCM + 厂商通道，或退化为 IM 通道 |
| C5 | 本机 **owner** 的 Remote 调用**没有可插拔的授权点** | ① `/api` channel 只允许一个 interceptor（`rpc-host.ts:293-295`），已被 Gateway 的 Host 入口占用；② `requestRejection()` 是只读查询（`rpc-host.ts:123`）；③ Gateway README 第 33 行：*"An owner call is dispatched without resource resolution or a decision."* | 锁屏只承诺「界面锁 + 网关锁 + 动作闸」，**不承诺本机接口锁**；威胁模型与文案如实标注（见 06 §3） |

结论：**C2/C3 反而把架构逼到了正确的方向**——不去 patch dsh 内部，而是像 `@dsh-remote/plugin` 那样做一个"自带协议和信任的旁路网关"。这条路的脆性最低。

## 1. 需求逐条可行性判定

| # | 需求 | 判定 | 关键依据 | 主要风险 |
|---|---|---|---|---|
| 1 | 管理并使用多台 PC 上的 dsh | ✅ 可行 | dsh 侧无「账号」，但每台 PC 就是一个独立 host；App 侧维护设备注册表即可 | 设备多了以后状态噪声大（Qoder 用统一账号解决，我们只能靠 UI） |
| 2 | 密码访问 + 安全机制 | ✅ 可行 | 插件独占自己的网关，鉴权完全自定义；可做到"设备密钥 + 密码 + E2E" | 自签 CA 在 iOS 上要用户装描述文件（或走指纹固定 + 纯 TLS） |
| 3 | 互联网 + 局域网 | ✅ 可行 | 局域网直连 WSS；公网靠中继（自建）或用户自备隧道 | 中继要自己运维；NAT 穿透不能靠打洞（成功率低） |
| 4 | 上传文件到对应机器的 dsh 工作区 | ⚠️ 可行但有成本 | 官方只读（C1）；官方附件通道落 `DSH_HOME` 而非工作区（`attachment-local`） | 路径逃逸、软链、大文件、断点续传都要自己做 |
| 5 | 手机 + 平板 + 触屏 | ✅ 可行 | uni-app 一套代码三端；平板用分栏 | 平板分栏在 uni-app 里要手写断点布局，不能靠 rpx 自适应 |
| 6 | 支持安装插件（机制参考 dsh） | ✅ 意外地容易 | `plugin-manager` 有 **12 个 `@Remote` 方法**（`src/index.ts:267-685`），含 `inspect / installBundle / cancelInstall / removeBundle / setBundleEnabled` | 远程装插件 = 远程执行代码，必须做权限分级 + 二次确认 |
| 7 | 参照/集成 dsh-mobile 的能力 | ✅ 可行 | dsh-mobile 的配对、设备管理、扩展协议、诊断都是可借鉴的成熟实现 | 直接复用其扩展目录会与其抢占服务名，需协商命名空间 |
| 8 | App 炫酷视觉（参照 dsh-startup-moss） | ✅ 可行且成本低 | moss 的视觉全部由 CSS 变量 + 伪元素 + Canvas 构成，**零图片依赖**；`theme.overrideTokens()` 是官方换肤接口（`lib/theme.js:1-40`，206 个 `--dsw-*`） | uni-app 的 nvue 不支持 `mix-blend-mode`/`radial-gradient`，必须全走 WebView 渲染；低端机需降级（见视觉 §6） |
| 9 | dsh 锁定态（锁的是 dsh 的操作能力，不是操作系统锁屏） | ⚠️ 分层可行，**有一处做不到** | 界面锁、远程锁、动作闸三层都能完整实现；但 dsh **不给 owner 调用链留钩子**，本机已登录浏览器的 API 调用无法被服务端拦截 | 详见 06 文档 §3 威胁模型：T3/T4 类对手挡不住，产品文案必须如实说明 |
| 10 | App 查看具体执行过程 + 会话消息发送队列 | ✅ 可行，**队列必须自研** | 执行过程的数据源是 dsh 的 session 事件流（`sessionController.follow/page`，`RemoteStream` + 分页历史）；但 **dsh 一次只接受一条 prompt**，没有排队概念 —— 队列只能在插件侧实现（内存 + 落盘） | 原始事件是 dsh 内部形状，小版本会变 → 必须在插件侧归一化成 `TraceItem`，不让它泄漏进协议 |
| 11 | App 浏览工作区/会话产物文件 + git/GitHub 仓库 | ✅ 意外地顺 | `workspaceFiles` 的**只读面**（`read / readBytes / stat / list / changes`）恰好就是"浏览"需要的全部能力；git 走 `child_process` 只读命令；GitHub 走 REST + PC 侧 token | git 必须限定只读子命令白名单（`status/diff/log/show/branch`）；GitHub token 只存 PC、绝不下发、绝不进日志 |

> 需求 8/9 的可行性结论比 1–7 更硬，因为两者都不依赖 dsh 的内部行为：视觉是纯前端，锁屏的三层实现点全在**我们自己的网关和客户端**里。唯一需要 dsh 配合的那一项（本机接口拦截），恰好是它明确不开放的那一项。
>
> 需求 10/11 的可行性来源不同，值得单独说一句：**它们是"只读"需求，而只读恰是 dsh 唯一愿意开放的方向**。
> 需求 4（上传）之所以难，是因为它要写；需求 11（浏览）之所以顺，是因为它只读，`workspaceFiles` 把
> `read / stat / list / changes` 都摆出来了，只是 README 里那句 "exposes no mutation operation" 让它在需求 4
> 面前一文不值、在需求 11 面前刚刚够用。**同一个接口，在两个需求上的评价完全相反。**

## 2. 为什么必须"自带网关"（架构层面的可行性论证）

### 2.1 三条候选路线

| 路线 | 做法 | 优点 | 致命问题 |
|---|---|---|---|
| A. 透传 Web | App 用 `web-view` 直接加载 dsh 的 Web UI | 三天能做完，功能 100% | 不是 App，是套壳浏览器；无法做原生通知/多机/上传/插件管理；体验等于 pocket |
| B. **旁路网关（推荐）** | 插件起独立 WSS 网关，App 直连；宿主内侧调 dsh 服务 | 契约稳定、鉴权自主、可做原生交互 | 要复刻少量 UI（会话流、审批、文件） |
| C. 云中继优先 | 所有流量走中继，LAN 也走 | 实现最简单 | 局域网也绕公网，延迟与可用性都差；隐私叙事差 |

**选 B，并把 C 降级为"公网时的传输方式"**：同一套协议，两种承载（LAN 直连 / 中继转发）。这样 App 只写一套 transport，切换对上层透明。

### 2.2 网关能拿到什么（可行性证据）

dsh 的 `@Remote` 服务是 **in-process** 的 cordis 服务，插件可以直接 `ctx.get(...)` 调用，**不需要走 dsh 的 wire**。这就是旁路网关的合法性来源：

```ts
const sessions   = ctx.get('sessionController')    // list / create / prompt / cancel / follow / page
const workspaces = ctx.get('workspaceController')  // create / rename / delete / pin / archive
const registry   = ctx.get('workspace')            // list() / get() / create() —— 工作区读取在这里
const picker     = ctx.get('directoryPicker')      // list / pick / createDirectory —— 远程目录树
const files      = ctx.get('workspaceFiles')       // read / readBytes / stat / list / changes（只读）
const terminal   = ctx.get('terminalController')   // create / attach(RemoteStream) / close
const plugins    = ctx.get('pluginManager')        // inspect / installBundle / remove / setBundleEnabled
```

已核对的方法名（源码）：

- `session-controller/src/index.ts`：`list / search / create / rename / fork / prompt / cancel / page / follow / projections / attachment / updateQueue / selectModel / modelCatalog`
- `workspace-controller/src/index.ts`：`create / rename / delete / insertBefore / archiveSession / pinSession / unlock…`
- `workspace-files/src/index.ts:233-340`：`read / readBytes / stat / list / changes`（**无写入**）
- `terminal-controller/src/index.ts`：`create / attach`（`attach` 返回 `RemoteStream`，双向）
- `plugin-manager/src/index.ts:267-685`：12 个 `@Remote`，含完整的安装生命周期

**这意味着需求 1/2/3/6 的核心能力全部有官方出口，不需要逆向。**

### 2.3 唯一必须自己补的：写入

`workspaceFiles` 明确 "exposes no mutation operation"；`attachment-local` 把附件存在 `DSH_HOME` 下（`join(root,'files',sha256…)`），不是工作区。所以"把手机文件放进项目目录"这件事，官方没有出口。

结论：插件必须提供 `fs.write` 类通道。这不算违规——插件本身就有宿主进程权限；风险不在能不能，而在**路径必须被工作区根约束**（详见技术方案 §7）。这也是本项目唯一需要写"危险代码"的地方。

## 3. 平台能力可行性（uni-app 视角）

| 能力 | Android | iOS | HarmonyOS | 结论 |
|---|---|---|---|---|
| WebSocket (WSS) | ✅ | ✅ | ✅ | 主通道可用 |
| 自签证书 + 指纹固定 | ✅ 可自定义 TLS 校验（需原生插件/uts） | ✅ 同上 | 🟡 | **最大不确定项**，见 §4.1 |
| 文件选择/拍照 | ✅ | ✅ | ✅ | 上传入口没问题 |
| 大文件分片上传 | ✅ | ✅ | ✅ | 需自己实现 |
| 扫码 | ✅ | ✅ | ✅ | 配对入口 |
| 本地通知 | ✅ | ✅ | ✅ | 任务完成提醒 |
| 远程推送 | ✅ FCM/厂商 | ✅ APNs | 🟡 | 需服务端，MVP 可先不做 |
| 生物识别 | ✅ | ✅ | ✅ | 免密解锁 |
| 后台保活长连接 | 🟡 厂商限制 | ❌ 严格限制 | 🟡 | **不能依赖**，必须"通知唤醒 + 重连" |
| `web-view` 沙箱 | ✅ | ✅ | ✅ | App 插件机制的载体 |
| 动态加载 JS | ❌ | ❌ | ❌ | App 端插件只能走声明式或 web-view |

两条从表里读出来的产品结论：

1. **iOS 后台长连接不可靠 → 推送是功能而非优化。** 没有推送，"任务跑完了"这件事在 iOS 上就是不可达的。MVP 至少要做本地通知（App 在前台/刚退到后台时）+ 重连补拉。
2. **App 端插件不能动态加载原生代码 → "插件机制参考 dsh" 必须降级成两档**：声明式面板（安全）+ web-view 沙箱（表达力）。这两档在后面技术方案里给具体协议。

## 4. 四个真实风险（及对策）

### 4.1 风险一：自签证书在 iOS 上不好办

局域网直连意味着 `wss://192.168.1.20:7443`，证书只能自签。

- 方案 A：让用户装 CA 描述文件 —— 体验灾难，不可接受。
- 方案 B：**不做系统级 TLS 信任，只做应用层指纹固定**（在 App 内自己校验证书指纹，不交给系统）。uni-app 默认不支持自定义校验，需要 uts 原生插件或 `plus.net` 的底层能力。
- 方案 C：**局域网走明文 WS + 应用层 E2E 加密**（Noise/X25519），公网走 TLS。这样既绕开证书问题，安全性反而更好（端到端，中继也看不懂）。

**推荐 C。** 这是 `@dsh-remote/plugin` 已经验证的思路（中继只见密文），我们把它用到局域网。代价：需要自己实现一层加密（libsodium/tweetnacl，JS 实现即可，握手和心跳流量极小）。

### 4.2 风险二：远程装插件 = 远程 RCE

`pluginManager.installBundle()` 会在宿主执行 pnpm、跑依赖构建脚本、加载进程内代码。手机上一个误触，等于把一台机器交出去。

对策（三条必须同时有）：
1. **权限分级**：设备分 `viewer / operator / admin`，只有 `admin` 能看到插件页。
2. **二次确认 + 信息充分**：安装前展示 `inspect()` 的 name/version/registry/bundle 声明，用户必须看到"这个包会以你的用户权限运行"。
3. **默认关闭**：`allowRemotePluginInstall: false`，需在电脑前手动打开，且可设"仅允许官方 registry"。

> 这条不是技术难点，是产品红线。dsh 官方对 `plugin_manager` 工具都要求 `danger-full-access` 或审批，我们没理由更松。

### 4.3 风险三：多机管理的"状态噪声"

Qoder 和 WorkBuddy 都靠**统一账号**把多机变简单（登录即绑定，绿色圆点即在线）。我们没有账号。

- 后果：设备列表的可信度全靠"配对记录 + 心跳"，离线判定会抖。
- 对策：**三层状态**（设备级 / 会话级 / 轮次级），可达性以"网关握手"为唯一真值（不做 ICMP，不猜）；状态过期用"检测中"而不是"离线"，避免误报（dsh-mobile 的设备列表正是这么做的）。

### 4.4 风险四：iOS 审核与"远程控制"定位

App Store 对"远程控制电脑"类应用审查较严（需要说明用途、数据流向、是否有企业分发）。

- 对策：定位成"**AI 任务远程查看与授权**"而非"远程桌面"；不提供屏幕串流、不提供任意 shell（终端功能做成 P1，且默认关闭、需 admin）；隐私清单如实申报（局域网、文件、相机）。
- 备选：先发 Android + 企业内测（TestFlight），iOS 正式版滞后一个版本。

## 5. 与竞品的可行性对照

| 维度 | Qoder Mobile | WorkBuddy | **DSH Link（本项目）** |
|---|---|---|---|
| 配对方式 | 同账号，登录即绑 | 同账号，登录即绑（无扫码配对） | **扫码配对（无账号）** |
| 多机 | 统一账号下的设备 | 设备列表 + 在线圆点 + 切换 | 设备列表 + 通道优先级 + 并行会话 |
| 通道 | 云（官方托管） | 云（官方托管） | **LAN 直连 / 自建中继 / 自带隧道** |
| 上传 | 附件 + 产物预览 | 拍照上传 → 电脑处理 | **直写工作区 + 作为附件注入** |
| 插件 | 无（产品线固定） | 远程配置技能/专家/连接器 | **远程装/卸/启停 dsh 插件 + App 端插件沙箱** |
| 可控性 | 官方云，不可自托管 | 官方云 | **全自托管，可离线内网运行** |

差异化的落脚点很清楚：**别人卖"账号 + 云"，我们卖"自己的机器 + 自己的网"**。这决定了配对必须自己解决（没有账号），也决定了"上传到工作区"和"装插件"是我们可以做、他们不会做的功能。

## 6. 工作量结构（按依赖排，不按时间排）

```
M1 骨架  插件网关 + 配对 + 会话列表/对话 + LAN 直连          ← 决定项目成立
         + 视觉基线（双皮肤 tokens + 扫描线 + 终端框）        ← 成本极低，全程受益
M2 可用  审批/提问 + 断线重连 + 多机切换 + 文件上传
         + 锁屏 L1/L2（界面锁 + 网关强制）                    ← 与鉴权同一批代码
         + 执行过程 trace + 消息发送队列                      ← 需求 10，只读流 + 自研队列
         + 文件浏览（fs.stat/read）+ git 只读浏览             ← 需求 11 的前半
M3 完整  公网中继 + 设备管理/撤销 + 通知 + 平板分栏
         + 冷启动动画 + 雷达 + 生物识别解锁                   ← 体验层，可后置
         + 会话产物 diff 视图 + GitHub 远程仓库浏览            ← 需求 11 的后半（要 token）
M4 扩展  远程插件管理 + App 端插件沙箱 + dsh-mobile 能力接入
         + 锁屏 L3（分级动作闸）+ 审计 UI
```

关键路径只有一个：**配对 → 会话流 → 审批**。这三件事跑通，剩下的都是增量。

需求 8（视觉）刻意放在 M1 而不是最后：视觉 tokens 是一次性成本，早期建立后每个页面自动继承；放到最后做，等于把所有页面的样式重写一遍。需求 9（锁屏）的 L1/L2 与鉴权共用同一套会话与角色代码，因此并进 M2 最省。

需求 10（执行过程 + 队列）放 M2 的理由：**没有它，App 在 agent 跑长任务时是"瞎的"**——用户只能看到"正在运行"四个字，既不知道进展也无法继续表达想法。而它的成本主要在归一化层（把 dsh 事件映射成 `TraceItem`），一旦做完，聊天页和执行详情页共用同一份数据。

需求 11 拆成两半：**本地文件 + git 放 M2**（只读、无外部依赖），**GitHub 远程仓库放 M3**（要 token、要处理限流与网络失败）。把后者提前做，会让项目在能用的那天就背着"要配 token 才能看仓库"的门槛。

## 7. 结论

- **技术上可行**，核心能力都有官方出口（§2.2），唯一自研的危险面是文件写入（§2.3），可被工作区根校验约束。
- **架构上应选旁路网关**（路线 B），并让 LAN/中继共用一套应用层 E2E 协议，绕开 iOS 自签证书问题。
- **产品上有五条红线**：配对要短、多机状态要稳、上传要安全、装插件要设权限闸、锁屏别把主人锁在外面。
- **锁屏的语义要一次说清**：锁的是 dsh 的操作能力，不是操作系统。这一条如果含糊，后面每条实现都会歪（06 §0.1）。
- **只读需求几乎零成本，写入需求才是真成本**：需求 11（浏览）直接吃 `workspaceFiles` 的现成只读面，需求 4（上传）被迫自建通道。这解释了为什么本项目的工作量集中在"写"这一侧。
- **最大不确定性不是 dsh，是 iOS 后台与证书**（§4.1/4.4）。建议 M1 就用真机验证这两点，不要留到 M3。
- **唯一做不到的是 C5**：本机 owner 的接口调用不可拦截。这不是实现问题，是 dsh 未开放该钩子。锁屏的价值因此集中在「挡人」与「挡远程设备」，而不是「挡本机进程」——文案必须与之一致。
