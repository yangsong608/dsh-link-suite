## 0. 三个前置约定

### 0.1 协议是唯一契约，类型在 `shared/protocol`

宿主与 App **不允许**各自定义一份数据结构。所有跨进程形状都在
`shared/protocol/src/types.ts`，两侧 `import type` 同一份。

代价是：改协议 = 两侧同时升级。收益是：不会有"宿主返回 `{ok:1}`、App 读 `{success:true}`"这类事故。

`PROTOCOL_VERSION = 1` 起步，**只增不改**。删字段要等到大版本，且中间要经过一轮"标记废弃但不删"。

### 0.2 方法名是数据，不是函数

`METHODS` 是一个 `as const` 数组，`Method` 是它的联合类型。这带来两个硬保证：

- 宿主侧 `Record<Method, Handler>`：**漏实现一个方法，编译期就红**（本次新增 20 个方法时，
  这个约束立刻抓出了 20 个漏配，比任何 review 都可靠）。
- App 侧 `Method` 收窄：拼错方法名编译期就红。

### 0.3 一个动作只有一个执行点

| 动作 | 唯一执行点 | 谁都不能再写第二遍 |
|---|---|---|
| 锁定态放行判定 | `plugin/src/gateway/guard.ts` + `protocol/policy.ts` | 每个 handler 里写 `if (locked)` |
| trace 内容裁剪 | `plugin/src/trace/redact.ts` | 每个 handler 里判断 soft |
| 路径逃逸校验 | `plugin/src/fs/paths.ts` 的 `resolveInside()` | 每个 handler 里 `path.resolve` |
| git 子命令 | `plugin/src/repo/git.ts` 的白名单联合类型 | 任何地方拼字符串调 `exec` |

这条纪律看起来像洁癖，实际上是本项目**唯一能挡住安全漏洞的结构**——同类插件最常见的漏洞，
都是"某个新加的 handler 忘了写那句判断"。

## 2. 数据模型

### 2.1 宿主侧内存结构

```ts
// 进程内单例，apply() 时创建，dispose 时清空
interface HostRuntime {
  readonly hostId: string              // 持久化在 ~/.dsh/dsh-link/host.json
  readonly lock: LockService
  readonly gateway: Gateway
  readonly devices: Map<string, DeviceRecord>   // deviceId → 记录
  readonly sessions: SessionRegistry            // 活跃会话的订阅句柄
  readonly queues: Map<string, SendQueue>       // sessionId → 队列
  readonly traces: Map<string, TraceRing>       // sessionId → ring buffer
}

interface DeviceRecord {
  deviceId: string
  name: string
  role: DeviceRole
  publicKey?: string      // M2 才有；M1 只有共享密钥
  createdAt: number
  lastSeen: number
  revokedAt?: number
}
```

**为什么 `traces` 放内存而不是每次都问 dsh**：`session.trace` 会被频繁拉（用户来回切段）。
每次回放 dsh 的历史要重新解析一遍事件流，成本高且可能取不全。ring buffer 只保留最近
`trace.ringSize`（默认 2000）条，更早的走 `session.trace` 的 `hasMore` 标记让用户知道"看得到更早的，
但要重新握手"——这是一个诚实的取舍，不做假装能无限回溯。

### 2.2 落盘文件

| 文件 | 内容 | 权限 | 何时写 |
|---|---|---|---|
| `~/.dsh/dsh-link/host.json` | `{hostId, createdAt}` | 0600 | 首次启动 |
| `~/.dsh/dsh-link/lock.json` | `{password:{algo,salt,hash,N,r,p,keylen}, webauthn?}` | 0600 | 设置/修改密码 |
| `~/.dsh/dsh-link/devices.json` | `DeviceRecord[]` | 0600 | 配对/撤销/心跳（节流 30s） |
| `~/.dsh/dsh-link/queue/<sid>.json` | `QueueItem[]`（只存 `pending`/`failed`） | 0600 | 队列变更（节流 500ms） |
| `~/.dsh/dsh-link/audit.jsonl` | 每行一个 `AuditEvent` | 0600 | 追加写，永不修改 |

**队列为什么要落盘**：用户排了 3 条消息，然后 dsh 因为更新重启了。如果队列只在内存，
这 3 条就消失了——而用户以为它们已经发出去了。**这是最伤信任的一类 bug**（数据看起来成功但实际丢了）。

**`sent` 不落盘**：已发送的条目留在文件里只会越来越大，且没有价值（它已经是历史消息的一部分）。

**原子写**：所有 JSON 都是 `write tmp → fsync → rename`。直接 `writeFile` 到目标路径，
在断电时会留下半截 JSON，下次启动解析失败 → 用户的密码/队列全丢。

### 2.3 App 侧本地存储

| Key | 内容 | 存储位置 | 理由 |
|---|---|---|---|
| `dsh-link/prefs` | `{skinMode, light, lite}` | `uni.setStorageSync` | 视觉偏好，不敏感 |
| `dsh-link/devices` | `DeviceCard[]`（不含密钥） | 同上 | 冷启动先渲染缓存，再重连刷新 |
| `dsh-link/lastSession` | `{deviceId, sessionId}` | 同上 | 回到上次的会话 |
| 设备密钥 / 解锁票据 | — | **Keychain / Keystore**（`uni.getStorageSync` 不可用） | 这是唯一不能进普通存储的东西 |

**为什么设备列表可以进普通存储、密钥不行**：设备列表是"我连过哪些机器"，泄漏了只暴露信息；
密钥泄漏等于把机器交出去。前者被 Root/越狱后的读取风险可接受，后者不可接受。

**缓存必须标记新鲜度**。`DeviceCard` 里带 `cachedAt`，超过 60 秒的在线状态在 UI 上降级为
"上次看到在线"——不这么做，用户会把一个两小时前的"在线"当成现在。

### 2.4 数据保留

| 数据 | 保留策略 | 理由 |
|---|---|---|
| 审计日志 | 不自动删，按大小轮转（10 MB → `.1`） | 安全日志被自动删除 = 关键时刻没有证据 |
| trace ring | 每会话 2000 条，超出丢最旧 | 内存有限，trace 的用途是"刚才发生了什么" |
| 队列 | 会话结束后 24h 清空 | 用户可能第二天才想起来看"昨天那条为什么失败" |
| 设备记录 | 撤销后保留 30 天（标记 `revokedAt`） | 撤销是误操作时有救回窗口 |
| App 设备缓存 | 无上限（设备数通常 < 10） | — |

## 3. RPC 契约

### 3.1 通用约定

**参数校验**：每个 handler 入口用 zod-lite（手写）校验，失败抛 `rpc/bad-args`，
message 必须写清"哪个字段、期望什么、收到什么"。这条不是洁癖——手机上出现
"参数错误"四个字时，用户和开发者都无法定位。

**幂等性分级**（决定重连时能不能安全重发）：

| 级别 | 方法 | 断线重连时 |
|---|---|---|
| 天然幂等 | 全部 `*.list` / `*.status` / `*.info` / `fs.read` / `git.*` | 直接重发 |
| 幂等但需 requestId | `session.prompt`（宿主按 requestId 去重） | 重发，宿主返回上次结果 |
| 不幂等 | `fs.upload` / `plugin.install` / `session.cancel` | **不自动重发**，UI 提示"结果未知，请刷新确认" |

`session.prompt` 必须带 `requestId`（客户端生成的 UUID）。宿主维护 5 分钟的
`requestId → result` 表，重发时命中即返回原结果。不这么做，网络抖动会导致同一句话发两遍，
agent 把同一个任务做两次——这是最难向用户解释的 bug。

**超时**：默认 20s；`fs.read` / `git.diff` / `session.trace` 放宽到 60s；
`plugin.install` 不设超时（走事件流，不是 RPC 返回）。

**错误**：一律 `RpcError(code, msg, details)`。`msg` 是给人看的中文，
`details` 是给程序用的结构化补充。客户端只按 `recoveryFor(code)` 的四类动作处理，
不为每个 code 写分支。

### 3.2 连接与设备

```ts
// device.info —— 豁免方法，握手后第一个调用
req:  {}
res:  HostInfo {
        hostId: string
        name: string
        platform: string          // 'darwin' | 'win32' | 'linux'
        dshVersion: string
        linkVersion: string
        caps: Caps                // 缺项即不支持，见 methods.ts
        lock: LockState
      }
err:  —
```

**`caps` 是 App 渲染的前提**：拿到 `caps.trace = 0` 就不显示"执行过程"段，
而不是点进去看到空页。这是"能力协商"的全部意义。

```ts
// device.list —— admin
res: DeviceInfo[]
```

```ts
// device.revoke —— admin + unlocked
req:  { deviceId: string }
res:  { ok: true }
err:  auth/forbidden（试图撤销自己）/ session/busy（该设备有活跃连接且未 force）
```

撤销自己的判定要**在宿主做**，不能在 App 里灰掉按钮——App 的判断可以绕过。

```ts
// pair.start / pair.finish —— 都要求 unlocked
// 理由：锁定时允许配对 = 在锁上装了个新锁孔
req:  pair.start  → { deviceName: string; platform: string }
res:  pair.start  → { pairId: string; code: string; expiresAt: number }   // code 是 6 位数字
req:  pair.finish → { pairId: string; code: string; answer: string }      // answer 是 SAS 指纹
res:  pair.finish → { deviceId: string; role: DeviceRole; secret: string } // secret 只返回这一次
```

### 3.3 锁定

```ts
// lock.status —— 豁免
res: LockState

// lock.unlock —— 豁免
req:  { password: string }
res:  { ticket: string; expiresAt: number }
err:  lock/bad-password（details.attemptsLeft）
      lock/rate-limited（details.retryAfterMs）
      lock/no-password-set

// lock.request —— 豁免；由 App 发起，等 dsh 界面上的人确认
req:  { deviceLabel: string }
res:  { unlocked: true }
err:  lock/request-timeout（30s 内无人确认）

// lock.lock —— operator + read（不要求 unlocked：锁自己是安全动作）
req:  { reason?: 'manual' | 'remote' }
res:  LockState
```

`lock.lock` 故意不要求 `unlocked`：**锁自己永远是允许的**。要求解锁才能锁，等于"忘了锁、
又记不住密码"时就永远锁不上。

### 3.5 会话

```ts
// session.list —— viewer
req: { workspaceId?: string; status?: SessionStatus }
res: SessionSummary[]

// session.prompt —— operator + unlocked，幂等（requestId）
req: {
  sessionId: string
  text: string
  attachments?: Array<{ fsPath: string; name: string; mime: string }>
  requestId: string            // 客户端 UUID，宿主 5 分钟内去重
}
res: {
  accepted: true
  queued: boolean              // true = 会话忙，进了队列
  queueItemId?: string         // queued 时返回，用于后续 edit/remove
  messageId?: string
}
err: queue/full（已满 20 条）
```

**`session.prompt` 在忙时不报错、而是入队**。这是需求 10 的核心交互决定：
如果返回 `session/busy`，App 就必须让用户"等一会儿再发"，而人在等的时候想到的三件事会忘。

```ts
// session.cancel —— operator + unlocked，不幂等
req: { sessionId: string }
res: { canceled: boolean }

// session.follow —— viewer，流式（对话流，不是 trace）
req: { sessionId: string; cursor?: number }
res: 流。帧类型 session.frame，payload 是 StreamItem

// approval.answer —— approver + unlocked
req: {
  sessionId: string
  approvalId: string
  decision: 'approve' | 'reject'
  /** 只对某些审批有意义（如"批准并记住这个命令"） */
  remember?: boolean
}
res: { ok: true }
err: session/not-found（审批已超时失效）
```

### 3.6 执行过程

```ts
// session.trace —— viewer（结构类，半锁允许）
req: {
  sessionId: string
  since?: number          // 只取 seq > since 的；断线续传用
  limit?: number          // 默认 100，上限 500
}
res: TracePage {
  items: TraceItem[]      // 半锁时每条都带 redacted: true，内容字段被清空
  nextSeq: number
  hasMore: boolean        // 还有更早的（向上翻）
  running: boolean        // 这一轮还在跑 → App 保持订阅
}
err: trace/not-found（会话不存在或已被清理）
```

**用 `since` 而不是 `offset`**：offset 分页在"新条目不断插入"的场景下会重复或跳过。
断线 30 秒后重连，用上次的 `nextSeq` 作为 `since`，一条不漏一条不重。

```ts
// session.trace.detail —— viewer + unlocked（内容类）
req: { sessionId: string; seq: number }
res: TraceDetail {
  seq: number
  text: string            // 完整入参/输出/终端日志
  truncated: boolean      // 超过 trace.maxDetailBytes
  bytes: number
}
err: trace/not-found（ring 里已被挤掉）
```

**为什么详情要单独拉**：一轮任务里 `npm install` 的输出可能有 200 KB。
如果随 trace 列表一起下发，一次翻页就会撞上 256 KiB 的帧上限，整条流断掉。
列表只带 40 行尾部，点开才拉全文——这是分页在这套协议里的第二次应用（第一次是文件）。

### 3.7 消息队列

```ts
// session.queue.list —— viewer（结构类，半锁允许）
req: { sessionId: string }
res: { items: QueueItem[]; max: number }

// session.queue.push —— operator + unlocked
req: { sessionId: string; text: string; attachmentCount?: number }
res: { item: QueueItem }
err: queue/full

// session.queue.edit —— operator + unlocked
req: { sessionId: string; itemId: string; text: string }
res: { item: QueueItem }
err: queue/not-found / queue/immutable（sending 中）

// session.queue.remove —— operator + unlocked
req: { sessionId: string; itemId: string }
res: { removed: true }
err: queue/not-found / queue/immutable

// session.queue.reorder —— operator + unlocked
req: { sessionId: string; itemId: string; toIndex: number }
res: { items: QueueItem[] }      // 返回全量，避免客户端自己算顺序
err: queue/immutable

// session.queue.clear —— operator + unlocked
req: { sessionId: string; includeFailed?: boolean }
res: { removed: number }
```

**`reorder` 返回全量而不是 `{ok:true}`**：拖动排序的客户端如果自己算顺序，
一旦与宿主不一致（比如另一台手机同时在操作），界面会显示一个宿主不存在顺序。
返回全量让"以宿主为准"变成结构上的保证。

**`clear` 默认不清 `failed`**：失败条目是用户需要看到的，批量清空只清待发的。
`includeFailed: true` 才连失败一起清。

### 3.8 会话产物

```ts
// session.changes —— viewer（结构类：只有路径与行数）
req: {
  sessionId: string
  /** 只看某一轮；不传则为整个会话累积 */
  turn?: number
}
res: {
  changes: FileChange[]       // path / op / additions / deletions / from
  truncated: boolean          // 超过 500 个文件
}

// session.diff —— viewer + unlocked（内容类）
req: { sessionId: string; path: string }
res: GitDiff                  // 复用 git 的形状：patch/additions/deletions/binary/truncated
err: fs/not-found / git/too-large
```

**`session.changes` 的数据来源是 trace 的 `file` 事件，不是 `git status`**：

| 来源 | 优点 | 缺点 |
|---|---|---|
| trace 的 `file` 事件 | 精确到"这个会话改的"，不受用户其他操作干扰 | 只覆盖 agent 主动改的文件；用户手动改的看不到 |
| `git status` | 全量 | 混入了用户在编辑器里手动改的、以及上一次会话遗留的 |

选 trace 为主、`git status` 作为兜底（会话没有 trace 时）。**这个决定要在 UI 上说清**：
"本轮产物"是"agent 改的文件"，不是"工作区里所有改过的文件"。

### 3.10 仓库与 git

```ts
// repo.list —— viewer（结构类）
req: { scope?: string }        // 不传 = 所有工作区
res: RepoSummary[]
// kind: 'workspace' | 'nested' | 'github'
// 只扫工作区内，除非 config.repo.allowOutsideWorkspace

// repo.info —— viewer
req: { repoId: string }
res: RepoSummary & { root: string; worktrees?: number }

// git.status —— viewer（结构类）
req: { repoId: string }
res: GitStatus {
  branch, head, upstream?, ahead, behind,
  staged: FileChange[], unstaged: FileChange[],
  untracked: string[], conflicted: string[]
}
err: git/not-a-repo / git/unavailable（宿主没装 git）

// git.diff —— viewer + unlocked（内容类）
req: { repoId: string; path?: string; staged?: boolean; commit?: string }
res: GitDiff {
  path, patch, additions, deletions,
  binary, truncated, change
}
err: git/too-large（超 maxDiffBytes 且无法有意义截断）

// git.log —— viewer
```

## 4. 状态机

### 4.1 设备连接（App 侧）

```
                 ┌──────────── pair.finish 成功 ────────────┐
                 ▼                                          │
  [未配对] ──► [connecting] ──ws open──► [handshaking] ──device.info──► [online]
                   ▲   │                      │                          │  ▲
                   │   └── 失败/超时 ─────────┘                          │  │
                   │            │                                        │  │
                   │            ▼                                        │  │
                   └──────── [offline] ◄──── 心跳超时 / ws close ────────┘  │
                                │                                          │
                                └──────────── 指数退避重试 ────────────────┘
```

退避序列 `1s → 2s → 4s → 8s → 16s → 30s（封顶）`，每次 ±20% 抖动。
**抖动必须有**：三台手机会在同一秒重连同一个宿主，不抖动就是自己 DDoS 自己。

`handshaking` 是一个独立状态而不是 `connecting` 的子阶段，因为它在 UI 上有独立表现：
"正在验证设备"和"正在连接" 对用户的含义不同（前者可能失败在密码，后者可能失败在网络）。

### 4.2 锁定态（宿主侧，唯一真相源）

```
                    ┌─────────────── 手动 ⌘⇧L / lock.lock ───────────────┐
                    │                                                     │
  [unlocked] ──空闲 idleMinutes──► [locked] ◄── 远程请求被批准 ────────────┘
      ▲   │                          │  ▲
      │   │                          │  │
      │   └── 空闲 softLockHours ──► [soft-locked]
      │                                 │
      └──── lock.unlock 成功（密码/票据/PC 确认）────┘
```

三个状态与四个原因（`LockReason`）：

| 进入原因 | 触发者 | 落到哪个态 |
|---|---|---|
| `idle` | 空闲计时器 | `soft-locked`（超过 softLockHours）或 `locked`（超过 idleMinutes） |
| `manual` | 人或 `⌘⇧L` | `locked` |
| `remote` | 手机请求 + PC 确认 | `locked` |
| `boot` | 启动时 | `locked`（有密码时）；无密码则始终 `unlocked` |

**两个计时器而不是一个**：`idleMinutes`（默认 10）→ 锁；
`softLockHours`（默认 8）→ 先进入半锁。两个计时器都 `unref()`，
否则它们会阻止 Node 事件循环退出，dsh 关不掉。

**唯一真相源在宿主**：客户端半（`lock-ui.js`）每秒轮询 `GET /dsh-link/lock`，
不做本地状态推断。这看起来"笨"，但它保证了一件事——**任何时候界面显示的状态都是宿主的状态**，
不存在"两个地方各记一份、然后不一致"的经典 bug。

### 4.3 会话队列（宿主侧）

```
push ──► [pending] ──会话空闲 && autoStart──► [sending] ──prompt 成功──► [sent] ──► 从队列移除
            │  ▲                                 │
            │  └────── edit / reorder ───────────┘（仅 pending 可改）
            │                                    └──prompt 抛错──► [failed]
            └────── remove ──────► [canceled] ──► 从队列移除
```

关键时序（**先置位，再 await**）：

```ts
async drain(): Promise<void> {
  const head = this.#items.find((i) => i.state === 'pending')
  if (!head) return
  head.state = 'sending'          // ← 必须在 await 之前
  try {
    await this.#send(head)
    head.state = 'sent'
  } catch (e) {
    head.state = 'failed'
    head.error = msg(e)
  }
  this.#persist()
}
```

如果先 `await this.#send()` 再改状态，两个 idle 事件并发触发的 `drain()` 会同时拿到同一条
`pending`，导致同一条消息发两遍。这是队列类代码最经典的 bug，且只在"任务刚结束的那一瞬间"
复现——手工测试几乎测不出来，必须靠单测（`tests/queue.test.mjs` 里有一条专门测这个）。

**`sent` 不入 `#items`**：出队而不是留在数组里。留在数组里会让 `queue.list` 返回一堆
历史条目，而 App 的队列条只想显示"还没发的"。

### 4.4 trace 订阅（App 侧）

```
[未订阅] ──进入会话/执行过程段──► [拉历史 session.trace(since)] ──► [订阅 chan.open('trace')]
                                                                         │
                          ┌──────────────── 收到 evt(seq > lastSeq) ────┘
                          ▼
                    [追加到本地列表] ──running=false──► [结束，保留列表]
                          │
                          └──ws 断开──► [重连] ──► 用 lastSeq 作为 since 补拉（不重不漏）
```

**用 `seq` 去重而不是时间戳**：宿主与手机时钟一定不同步，用时间做游标会出现
"补拉回来的一批全被判为旧数据丢掉"或"重复追加"。`seq` 是同一个计数器发出来的，天然有序。

**本地列表有上限**（默认保留 1000 条）：用户在一个会话里待三小时，trace 可能有几万条，
全留会 OOM。超出时丢最旧的，并在顶部显示"更早的步骤已折叠"——诚实，不假装全都在。

### 4.5 git 视图刷新

```
[打开仓库] ──git.status──► [显示]
     ▲                        │
     │                  用户下拉 / 切回前台 / 订阅到 file 事件
     │                        ▼
     └────────────────── [重新 git.status]（节流 2s）
```

**不做文件监听（fs.watch）**：工作区可能在网络盘上，`fs.watch` 在网络盘上不可靠且吃 CPU；
而 agent 改文件这件事我们本来就能从 trace 的 `file` 事件知道。用事件驱动 + 手动下拉，
比轮询整个仓库便宜两个数量级。

## 5. 核心算法

### 5.1 dsh 事件 → TraceItem（完整映射表）

这是需求 10 最核心的一张表。左边是 dsh 的事件类型，右边是我们的归一化结果。

| dsh 事件 | TraceItem.k | 关键字段映射 | 备注 |
|---|---|---|---|
| `assistant-thinking` | `think` | `summary` 截 300 字 | 完整思维链**不下发**，只给摘要 |
| `assistant-text` | `text` | `delta`/`text`，`partial` → `streaming` | 流式增量直接透传 |
| `tool-call` | `tool` | `name`→`tool`，`input.path`→`target`，`input` 截 200，`result.text` 截 400 | 最大的截断在这里 |
| `file-changed` | `file` | `path`/`op`/`additions`/`deletions`/`from` | 不截断，这是半锁下唯一要给的 |
| `terminal` | `term` | `cmd` 截 200，`output` 取尾 `maxTailLines` 行 | 全量走 detail |
| `approval-request` | `approval` | `id`/`command`/`risk` | — |
| `question` | `question` | `id`/`question`/`options`/`multiSelect` | — |
| `error` | `error` | `code`/`message` 截 300 | — |
| `turn-complete` | `note` | `text` 合成"本轮完成 · 3 个文件 · 42s" | 让列表有明确的段落边界 |
| **其它（未知）** | `undefined`（丢弃） | — | **绝不抛错**，见下 |

**未知事件必须丢弃而不是抛错**。dsh 加一个新事件类型是常态（比如某天加了
`context-compacted`）。如果归一化层遇到未知类型就抛错，整个 trace 流会断，
用户看到的是"执行过程页空白"——而根因只是一次无害的 dsh 小版本升级。

这条要写成测试：`assert.equal(normalize({type:'some-new-thing'}, 1), undefined)`。

**`seq` 由我们自己发**，不用 dsh 的字段。dsh 的事件序号语义没有文档保证，
依赖它等于把自己的正确性绑在别人的实现细节上。我们用一个会话内的 `MonotonicCounter`，
从 ring buffer 的最后一个 seq + 1 继续。

### 5.2 半锁裁剪（redact）

```ts
export function redact(item: TraceItem): TraceItem {
  switch (item.k) {
    case 'text':  return { ...item, text: '', redacted: true }
    case 'think': return { ...item, summary: '', redacted: true }
    case 'tool':  return { ...item, input: undefined, output: undefined, redacted: true }
    case 'term':  return { ...item, tail: undefined, redacted: true }
    default:      return item
  }
}
```

**保留哪些、清掉哪些，判断标准是"这句话会不会泄漏文件内容"**：

| kind | 保留 | 清掉 | 理由 |
|---|---|---|---|
| `text` | `streaming` | `text` | 助手说的话可能包含密钥、代码 |
| `think` | 「思考了 2.4s」 | `summary` | 推理摘要常常引用文件内容 |
| `tool` | `tool`/`target`/`ms`/`ok` | `input`/`output` | **`target` 要保留**：用户需要知道它碰了哪个文件 |
| `term` | `cmd`/`exit` | `tail` | 命令行本身不敏感，输出才敏感 |
| `file` | 全部 | — | 只有路径与行数，这正是半锁要给的信息 |
| `approval` | 全部 | — | 审批本来就是要去 PC 上处理的事，手机上看到命令无害 |
| `question` | 全部 | — | 问题文本是 agent 主动问的，不含文件内容 |
| `error` | `code` | `msg` | 错误信息经常带路径与片段 |

`tool.target` 保留是一个**刻意的例外**：严格说路径也是信息，但如果不给路径，
半锁下的 trace 就退化成"它用了个工具，成功了"——那用户还是会回电脑前看。
而路径本身在 `fs.list` 下本来就可见（半锁允许），不算新增泄漏。

### 5.3 队列调度

```
触发源：
  a) sessionController 的 idle 事件（首选）
  b) 客户端 push 时，若会话当前空闲 → 立即尝试 drain
  c) 兜底定时器 5s 一次（防止事件丢失）

约束：
  - 同一会话同时只有一个 drain 在执行（单飞）
  - 一次 drain 只发一条，发完等下一次 idle
  - failed 不参与 drain
```

**为什么一次只发一条**：agent 收到第二条消息时，第一条可能还在上下文里没消化完。
连发两条等于让 agent 同时处理两件事，它会自己决定先做哪个——这不是排队，这是混乱。
"一次一条"让队列的语义变得可预测。

**兜底定时器的必要性**：dsh 的 idle 事件可能因为版本差异或订阅失败而收不到。
一个 5 秒的兜底让"队列卡住"变成一个可观察、可自愈的状态，而不是要用户手动点。

### 5.4 文件分片与二进制探测

```ts
export async function statFile(abs: string): Promise<FileStat> {
  const st = await fs.stat(abs)
  const mime = mimeOf(abs)

  // 1) 二进制判定：读开头 probeBytes，找 NUL
  const probe = await readFirst(abs, cfg.files.probeBytes)
  const binary = probe.includes(0)

  // 2) 行数：只在文件不太大时统计
  //    为一个 2GB 的日志数行数会阻塞事件循环几十秒，用户看到的是"整个 App 卡死"
  const lines = binary || st.size > cfg.files.maxCountLinesBytes
    ? 0
    : await countLines(abs)

  // 3) 是否受版本控制
  const tracked = await isTracked(abs)

  return { path: abs, kind: st.isDirectory() ? 'dir' : 'file',
           size: st.size, mtime: st.mtimeMs, mime, binary, lines, tracked }
}
```

**`lines: 0` 是一个约定**，含义是"没统计"，不是"空文件"。UI 必须据此**不显示**"共 N 行"，
而不是显示"共 0 行"。这类"0 有歧义"的设计要在类型注释里写死。

**分片读取的 offset 语义**是字节偏移，不是行偏移。看起来按行更自然，但实现上要在服务端
维护"第 N 行在第几字节"的索引，而文件随时可能被 agent 改。用字节偏移 + `eof` 标记，
客户端用"累积字节数"做进度，是唯一在文件变动时仍然正确的方案。

### 5.5 diff 截断

```
取到 patch 后：
  bytes > maxDiffBytes ?
    是 → 尝试只保留前 N 个 hunk，使总字节 <= maxDiffBytes
         → truncated: true（并在 UI 上显示"还有 12 个改动块未显示"）
    否 → 原样返回
```

**不做"掐断字符串"**：截断必须落在 hunk 边界上。掐断一个 hunk 会得到一个语法不完整的
diff，客户端渲染器可能抛错，或者显示出一段没有上下文的乱码。

二进制文件的 diff 直接返回 `binary: true` + `patch: ''`，不尝试生成文本 diff。

### 5.6 仓库发现

```
repo.list(scope):
  root = workspace.path(scope)
  1) git rev-parse --show-toplevel 在 root 上
       成功且 == root → { kind: 'workspace' }
       成功且 != root → 说明工作区在某个仓库的子目录里 → { kind: 'nested', path: toplevel }
       失败 → 没有 workspace 级仓库
  2) 扫 root 下深度 <= 2 的子目录，跳过 node_modules / .git / dist
       有 .git → { kind: 'nested' }
  3) 上限 20 个，超出截断并在结果里标记（避免 monorepo 里扫出 300 个）
```

**深度限制 2 的理由**：`packages/*/` 是 monorepo 的常见结构，深度 2 恰好覆盖；
再深的仓库（`packages/a/sub/`）罕见，而且扫下去的成本是 O(文件数)。

**跳过 `node_modules`** 不是可选项：一个中等项目有 3 万个目录，扫一遍要几秒，
而 `repo.list` 是要在打开页面时同步返回的。

## 6. 关键时序

### 6.1 首次连接

```
App                          Gateway                       dsh
 │── ws connect ─────────────►│
 │── hello{ver, deviceId} ───►│  (M1 无 E2E，M2 加握手)
 │◄───────── challenge ───────│
 │── auth{hmac} ─────────────►│  校验设备密钥
 │◄───────── ready ───────────│
 │── device.info ────────────►│──► 读 caps / lock
 │◄──── HostInfo ─────────────│
 │                            │
 │  caps.trace=0 → 不渲染执行过程段
 │  lock.locked=true → 设备卡显示"已锁定"
 │
 │── session.list ───────────►│──► store.list()
 │◄──── SessionSummary[] ─────│
```

**第一个业务调用必须是 `device.info`**，不能是别的。因为整个 UI 的可见性依赖 `caps` 和 `lock`，
在拿到它们之前渲染任何东西都可能渲染错（比如给一台锁定的机器显示"发送"按钮）。

### 6.2 发一条消息（会话忙时入队）

```
App                                Gateway                     dsh
 │── session.prompt{rid,text} ────►│
 │                                 │─ 会话在跑？ ──是──┐
 │                                 │                  ▼
 │                                 │            queue.push()
 │◄── {accepted, queued:true, ─────│            ──────────────
 │     queueItemId}                │
 │                                 │
 │  UI: 队列条展开，显示 1 条待发    │
 │                                 │
 │                    …… agent 这一轮结束 ……（idle 事件）
 │                                 │─ queue.drain()
 │                                 │    head.state = 'sending'   ← 先置位
 │                                 │    dsh.prompt(head.text)
 │                                 │    head.state = 'sent' → 出队
 │◄── evt queue.changed ───────────│
 │  UI: 队列条 -1；这条消息出现在对话流里
```

**为什么 `session.prompt` 和 `queue.push` 是两个方法**：
`session.prompt` 是"说一句话"，它自己会根据忙闲决定直接发还是入队；
`queue.push` 是"明确地排一条"。前者是主路径（输入框发送），后者用于"我确定现在不该打断它"。
两者最终写进同一个队列，只是入口不同。

### 6.3 看执行过程（含断线续传）

```
App                                Gateway
 │── session.trace{sid} ──────────►│  since 未传 → 返回最近 100 条
 │◄── TracePage{items,nextSeq, ────│
 │              running:true}      │
 │                                 │
 │   渲染 + 记 lastSeq = nextSeq    │
 │── chan.open{kind:'trace',sid} ─►│
 │◄── {chanId, credit} ────────────│
 │                                 │
 │   …… 新步骤 ……                   │
 │◄── evt trace.item{seq:101} ─────│   只推 seq > lastSeq 的
 │   lastSeq = 101                 │
 │                                 │
 │   ⚡ 网络断开                     │
 │   UI: 顶部显示"连接中断，正在重连" │
 │                                 │
 │── 重连 ────────────────────────►│
 │── session.trace{sid, since:101} ►│   ← 用 lastSeq 补拉，不重不漏
 │◄── TracePage{items:[102..150]} ──│
```

**断线期间不显示"加载中"**，显示"连接中断" + 已有的内容。用户至少还能看已拉到的部分，
而不是盯着一个转圈。

### 6.4 看文件

```
App                          Gateway                       磁盘
 │── fs.list{scope,path} ───►│──► workspaceFiles.list()
 │◄── FileEntry[] ───────────│
 │                           │
 │  用户点 package.json       │
 │── fs.stat ───────────────►│──► stat + 读 8KiB 探测 NUL
 │◄── FileStat{binary:false, │
 │     lines:42, tracked:true}│
 │── fs.read{offset:0} ─────►│──► read() 分页
 │◄── FileSlice{content, ────│
 │     eof:false}            │
 │                           │
 │  UI: 代码高亮 + "继续加载"  │
```

**先 `stat` 再 `read`**，不能跳过。跳过的话，用户点开一个 png 会拿到 base64 的 256 KB，
在文本渲染器里显示成一屏乱码——而 `binary` 标记本来能让 UI 直接换成图片查看器。

### 6.5 锁定与解锁

```
PC（dsh 界面）              Gateway                   手机
 │                             │                       │
 │ 空闲 10 分钟                 │                       │
 │◄── lock 状态变化 ────────────│                       │
 │ 客户端半：移除 #root，装锁屏   │── evt lock.changed ──►│ 设备卡变"已锁定"
 │                             │                       │
 │                             │◄── lock.request ──────│ 用户点"请求解锁"
 │ ◄── 显示确认框（30s）────────│                       │
 │ 用户点"允许"                 │                       │
 │── POST /dsh-link/lock/unlock│                       │
 │   （仅回环地址可调用）        │── evt lock.changed ──►│ 设备卡变"在线"
 │ 客户端半：摘锁屏，恢复 #root  │                       │
```

关键点：**手机发起的 `lock.request` 不能自己解锁**。它只是"敲门"，门里的人（PC 前的用户）
决定开不开。这是整套设计里唯一一处"必须有人在物理机器前"的动作，也是它作为安全机制成立的原因。

## 7. 失败与降级矩阵

这张表的用法：写每个页面时先查一遍，确认"这个失败我有对策吗"。**没有对策的失败就是白屏。**

| 失败 | 表现 | 降级策略 | 用户看到 |
|---|---|---|---|
| 宿主没装 git | `git/*` 返回 `git/unavailable` | `device.info` 时用 `execFile('git',['--version'])` 探测，把 `caps.git` 置 0 | 仓库入口不出现（不是灰掉） |
| 工作区不是 git 仓库 | `git/not-a-repo` | `repo.list` 返回空数组 | 仓库页显示"这个工作区没有版本控制" |
| 文件是二进制 | `fs.stat.binary = true` | 不给"按文本打开"，改给下载 | 直接显示文件大小 + 下载按钮 |
| 文件太大（> 256 KiB） | 分页 | 首屏只读第一页 | "已加载 1–200 / 3120 行 · 继续加载" |
| diff 超限 | `truncated: true` | 按 hunk 边界截断 | "还有 12 个改动块未显示" |
| trace ring 已挤掉 | `trace/not-found` | 提示 + 提供"重新拉取最近 200 条" | "更早的步骤已被清理 · 重新加载" |
| 队列满 | `queue/full` | 拒绝入队，但输入框保持可用 | "队列已满（20 条），先处理几条" |
| 消息发送失败 | `failed` + `error` | **不自动重试**，留在队列里 | 红色行 + 原因 + "重发"按钮 |
| 另一台设备同时改了队列 | 顺序不一致 | `reorder` 返回全量，强制以宿主为准 | 列表安静地重排（不弹窗） |
| GitHub token 失效 | `repo/auth` | 隐藏远程内容，保留本地仓库 | "需要重新配置 GitHub token（在电脑上）" |
| GitHub 限流 | `repo/auth` + `retryAfterMs` | 倒计时 | "触发限流，12 分钟后可重试" |
| **半锁时点开文件内容** | `lock/readonly` | 不报错弹窗，改成引导 | 内容区显示 `🔒 解锁后可查看` + 解锁按钮 |
| 宿主版本旧（无 trace） | `caps.trace = 0` | 段切换里只留"对话" | 没有"执行过程"这个 tab |
| ws 断开 | — | 保留已有内容 + 顶部条 | "连接中断，正在重连（第 3 次）" |
| dsh 重启（hostId 不变） | 会话全没了 | 刷新会话列表 | "dsh 已重启，会话已重置" |

**一条贯穿全表的规则：能力缺失表现为"不显示"，运行时失败表现为"能看懂的一句话"。**
两者不能混——把"不支持"做成"点了报错"，用户会以为是自己操作错了。

## 8. 性能预算

| 指标 | 目标 | 硬上限 | 测量点 |
|---|---|---|---|
| 首包（H5/App 冷启动 JS+CSS） | < 300 KB | 400 KB | `du -sh dist`，当前 280 KB |
| H5 首屏可交互 | < 1.2s | 2s | Lighthouse / 真机 |
| trace 列表渲染 | 100 条 < 16ms | 300 条 < 50ms | 虚拟滚动，只渲染视口内 |
| trace 事件吞吐 | 50 条/s 稳定 | 200 条/s 不崩 | 背压触发时合批（16ms） |
| 帧大小 | < 8 KB（常规） | 256 KiB（硬） | `rpc/too-large` 阈值 |
| 文件首屏 | < 300ms（本地文件） | 1s | 256 KiB 分页 |
| git.status（1 万文件仓库） | < 400ms | 2s | `execFile` + `maxBuffer` |
| `repo.list` 扫描 | < 200ms | 1s | 深度 2 + 跳过 node_modules |
| 队列落盘 | 异步不阻塞 | — | 节流 500ms |
| 内存（宿主插件） | < 40 MB（10 会话） | 100 MB | trace ring 2000/会话 |

**唯一的硬约束是"256 KiB 单帧"**：它是协议层写死的，超了直接 `rpc/too-large` 拒绝。
所以所有可能大的东西都必须分页：文件内容、diff、trace 详情、终端输出、安装日志。
这五个地方只要有一个忘了分页，用户就会在某天遇到"点开一个大文件，整个会话断线"。

## 9. 安全清单（实现级）

写代码时逐条对照。这些不是"建议"，每一条都对应一个具体的攻击或事故。

**路径**
- [ ] 所有用户传入的路径都过 `resolveInside(workspaceRoot, p)`：`path.resolve` 之后
      用 `startsWith(root + sep)` 判断，**不是** `startsWith(root)`（后者会让 `/app-evil` 通过 `/app` 的校验）。
- [ ] 逐段 `lstat`，遇到 symlink 就拒绝（除非 `followSymlinks` 显式打开）。
- [ ] Windows 上拒绝保留名（`CON`/`PRN`/`AUX`/`NUL`/`COM1`…）与结尾的空格/点。

**git**
- [ ] 只用 `execFile('git', ['-C', root, cmd, ...args, '--'])`，**永不** `exec` 拼字符串。
- [ ] `cmd` 来自字面量联合类型 `'status'|'diff'|'log'|'show'|'branch'|'ls-files'|'rev-parse'`。
- [ ] 参数逐项检查：拒绝 `-c`、`--exec`、`--upload-pack`、`--receive-pack`、`--config`。
- [ ] 路径参数放在 `--` 之后，防止被当成选项。
- [ ] 超时 8s + `maxBuffer` 限制，防止一个巨大仓库把宿主内存吃满。

**GitHub**
- [ ] token 只在宿主内存，不出现在任何 `RpcError.message` 里（错误 message 生成前先脱敏）。
- [ ] token 不写审计日志、不写 `devices.json`。
- [ ] `caps.gh = 0` 时 `repo.gh.*` 直接 `repo/unsupported`，连网络请求都不发。
- [ ] allowlist 非空时，未命中的仓库返回 `repo/unsupported`（不泄漏"存在但没权限"）。

**锁定**
- [ ] 锁定判定只在 `guard.ts`；`lockRejection()` 是唯一策略函数（宿主与 App 共用）。
- [ ] 半锁的内容裁剪只在 `redact.ts`，且**所有**返回 trace 的路径都过它。
- [ ] `lock.unlock` 的密码比较用 `timingSafeEqual`，长度不等也走一次假比较。
- [ ] 失败计数在**宿主**，客户端传来的 `attemptsLeft` 一律不信。
- [ ] `lock.request` 的解锁必须在 PC 端确认，且 30s 无响应自动拒绝。

**文件写入（上传）**
- [ ] 落盘用 `tmp + rename`，绝不直接写目标路径。
- [ ] 禁写 `.git/` 内部对象、`node_modules/`（可配置）、`.dshlink-tmp/`。
- [ ] 同名冲突不静默覆盖，返回 `fs/conflict` + 建议名。

**协议**
- [ ] 每个 handler 入口校验参数，错误 message 含字段名/期望/实际。
- [ ] 单帧 > 256 KiB 直接拒（`rpc/too-large`），不尝试截断。
- [ ] `session.prompt` 的 `requestId` 去重窗口 5 分钟，过期的 requestId 不参与去重（防止内存泄漏）。

**审计**
- [ ] `lock` / `unlock.ok` / `unlock.fail` / `unlock.limited` / `remote.request` / `device.paired` / `device.revoked` / `plugin.install` 全部落审计。
- [ ] 审计文件 `0o600`，只追加；写入失败**静默**（安全日志不能因为磁盘满就让业务失败）。
- [ ] 审计内容**不含**密码、token、文件内容、命令输出。

## 11. 实现顺序（按依赖，不按时间）

```
① protocol 补齐                      ← 已完成（24 项自检）
     types / methods / policy / errors / 测试

② plugin 骨架                        ← 已完成（编译 + 10 项自检）
     config / dsh 类型面 / lock / gateway / router 全 notImplemented

③ plugin 真实现（按此顺序）
     a. fs/paths.ts        逃逸校验          ← 一切文件操作的前提
     b. fs/read.ts         分片 + 二进制探测
     c. repo/git.ts        白名单 execFile
     d. repo/discover.ts   仓库发现
     e. trace/normalize.ts 事件映射 + redact
     f. queue/             状态机 + 落盘
     g. router 里把 notImplemented 逐个换掉
     h. repo/github.ts     （M3）

④ app 接真数据
     a. transport 打通 device.info + lock.*   ← 第一个端到端闭环
     b. sessions 页接 session.list
     c. chat 页接 session.follow
     d. trace 段接 session.trace + chan
     e. queue 条接 session.queue.*
     f. files 页接 fs.*
     g. repo 页接 repo.* / git.*

⑤ 视觉与原型对齐                     ← 已有基线，新页面按 08 补
```

**为什么 `fs/paths.ts` 排第一**：它是所有文件类方法的公共前置。先写它，后面每个 handler
都只有一行 `const abs = resolveInside(root, p.path)`；后写它，就会变成每个 handler 各写一遍
`path.resolve`，然后忘掉其中一个——而忘掉的那个就是漏洞。

**为什么第一个端到端闭环选 `device.info` + `lock.*`**：这五个方法宿主侧已经实现，
App 侧只需要 transport + 一个设备卡片。跑通它，就验证了握手、鉴权、帧编解码、错误传递
四条链路，而不用先做任何业务逻辑。**先打通最小闭环，再堆功能**，是这类跨进程项目唯一可靠的推进方式。
