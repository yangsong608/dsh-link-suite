# DSH Link · 技术方案

> 三个交付物：`dsh-link`（dsh 宿主插件，内含锁屏子系统）、`dsh-link-relay`（自托管中继，可选）、`dsh-link-app`（uni-app 移动端）。
> 本文给到可直接开工的粒度：协议、鉴权、数据模型、接口映射、关键代码骨架、部署与测试。
>
> 工程落点见 `00-项目总览.md`；视觉规格见 `05-视觉与动效-MOSS.md`；锁屏的威胁模型与三层强制点见 `06-锁屏与远程安全.md`。本文只保留与协议/架构相关的部分。

## 1. 总体架构

```
┌──────────────────────────── 手机 / 平板（uni-app） ────────────────────────────┐
│  设备 │ 会话 │ 对话 │ 执行过程 │ 队列 │ 文件 │ 仓库 │ 插件 │ 设置               │
│  ─────────────────────────────────────────────────────────────────────────     │
│  Transport（统一：帧编解码 + E2E + 重连 + 多路复用）                            │
│       ├─ LAN:    ws://<lan-ip>:7443/dshlink        （应用层 E2E）               │
│       ├─ WAN:    wss://relay/dshlink/<hostId>      （TLS + 应用层 E2E 双层）    │
│       └─ TS:     ws://100.x.x.x:7443/dshlink       （Tailscale 内网）           │
└───────────────────────────────────┬───────────────────────────────────────────┘
                                    │  一套协议，三种承载
┌───────────────────────────────────▼───────────────────────────────────────────┐
│                        dsh 宿主进程（Electron / CLI）                          │
│  ┌───────────────────────── dsh-link（插件） ─────────────────────────────┐    │
│  │  Gateway   WSS server :7443（可关）                                     │    │
│  │  Lock      锁定状态机（锁 dsh 的操作能力）/ 空闲 / 密码 / 票据 / 审计    │    │
│  │  Auth      配对 / 设备公钥 / 角色 / 密码(scrypt) / 票据 / 审计           │    │
│  │  Router    m → service 方法（白名单，非反射；锁定态过 guard）            │    │
│  │  Trace     dsh 事件 → TraceItem 归一化 + 半锁 redact + ring buffer      │    │
│  │  Queue     消息发送队列（内存 + 落盘，dsh 本身没有排队概念）             │    │
│  │  FsBridge  上传/下载/列目录/读文件（工作区根约束 + 原子落盘 + 分页）     │    │
│  │  RepoHub   git 只读白名单（execFile）+ GitHub REST（token 不出宿主）     │    │
│  │  PluginHub pluginManager 代理 + 安装日志流                               │    │
│  │  AppExt    下发 App 端插件清单（声明式 / web-view 包）                   │    │
│  │  Relay     （可选）主动出站连中继，NAT 后可用                            │    │
│  └──────────────────────────────┬──────────────────────────────────────────┘    │
│                                 │ in-process（不走 wire）                        │
│   sessionController · workspaceController · workspaceFiles · terminalController  │
│   pluginManager · agent/approval waterfall · workspace · fs · theme              │
└─────────────────────────────────────────────────────────────────────────────────┘
                                    │
                        ┌───────────▼────────────┐
                        │ dsh-link-relay（可选） │  只按 hostId 转发密文帧
                        └────────────────────────┘
```

**三条不可妥协的架构原则**

1. **不 patch dsh 内部**。不接管 `ctx.connection`、不改 `ctx.webServer.server`、不注入 `trustedHosts`。插件只做"自己的服务 + 调用别人的服务"。（对比：`dsh-remote-mobile` 接管 `connection`，脆性最高。）
2. **一套协议，多种承载**。LAN / 中继 / Tailscale 对上层完全一致，切换只换 endpoint。
3. **载荷级 E2E**。中继只见密文；局域网同样加密（顺带绕开 iOS 自签证书，见可行性 §4.1）。

## 2. 组件与职责

| 组件 | 语言/栈 | 职责 | 不做什么 |
|---|---|---|---|
| `dsh-link`（宿主插件） | TypeScript，cordis 插件 | 网关、鉴权、锁定、路由、trace 归一化、发送队列、文件、仓库代理、插件代理 | 不实现 agent、不代理浏览器 UI、不调 OS 锁屏 API |
| `dsh-link`（客户端半） | 浏览器 JS（`client/lock-ui.js`） | 界面锁层、焦点陷阱、解锁交互、皮肤跟随 | 不做任何密码比较（全在宿主） |
| `dsh-link-relay` | Node（单文件产物）/ Go | 按 `hostId` 转发帧、背压、在线状态 | 不落盘、不解析明文、不做鉴权 |
| `dsh-link-app` | uni-app（Vue3 + TS） | 设备/会话/对话/执行过程/队列/文件/仓库/插件 UI、本地缓存、通知 | 不缓存明文密钥到普通存储（走 Keychain/Keystore）；不持有 GitHub token |
| `@dsh-link/protocol` | TypeScript（纯类型 + 编解码） | 帧格式、方法名常量、错误码、E2E 封装 | 不依赖 dsh，不依赖 DOM/node 内置 |

> 锁屏是插件内的**子系统**（`plugin/src/lock/`），由 `config.lock.enabled` 开关；关掉 `config.gateway.enabled` 就只跑锁屏、不监听任何端口。网关侧通过 `ctx.get('dshLinkLock', false)` 软读取锁状态，锁屏未启用时视为永远解锁。
>
> **不拆成两个 cordis 条目**：同一个模块 apply 两次会在 Context 里建两套服务，反而更容易互相踩。config 开关足够表达"我只想用一个"。

**为什么网关是独立端口而不是复用 3080**

- 3080 的服务对象是浏览器 SPA（Cookie + 单 peer），我们服务的是原生客户端（设备密钥 + 多路复用）。
- 独立端口可以只监听 `127.0.0.1`（纯中继模式）或 `0.0.0.0`（LAN 模式），用户可一键关闭。
- 出问题时可整体关掉，不影响桌面使用。

## 3. 协议设计

### 3.1 握手（4 步，1-RTT 后加密）

```
App                                          Host
 │  ClientHello {v, hostId, deviceId?, na, caps}  │   明文（WAN 外层已有 TLS）
 │──────────────────────────────────────────────>│
 │  ServerHello {v, nb, hostPub, ephPub, salt, caps, needPair?}
 │<──────────────────────────────────────────────│
 │  —— 双方: sh = SHA256(ClientHello‖ServerHello)                    ——
 │  —— k  = X25519(appEph, hostEph)；mk = HKDF(k, salt, "dshlink/v1") ——
 │  —— SAS = 6 位十进制(HMAC(mk, sh))  ← 首次配对时两端显示，防 MITM ——
 │  Auth {deviceId, sig = Ed25519(sk, sh), ticket?, pwdProof?}
 │──────────────────────────────────────────────>│
 │  AuthOk {ticket, refresh, role, serverTime}    │
 │<──────────────────────────────────────────────│
 │  ==== 之后所有帧：XChaCha20-Poly1305(mk, counter, plaintext) ====
```

- **首次配对**必须带 `pwdProof`（密码）或 `pairProof`（二维码里的 256-bit `pairSecret`）。
- 6 位配对码路径：`pairSecret` 不存在时用 `code` 做 PSK 派生的确认值，两端比对 SAS。**SAS 不一致 = 有中间人，立即中止。**
- `caps` 做能力协商：`{fs:1, plugins:1, term:0, appext:1}`，老版本 App 连新宿主不会炸。

### 3.2 帧格式

控制帧（JSON，加密后发送）：

```jsonc
{ "t":"req",  "id":17, "m":"session.prompt", "p":{...} }
{ "t":"res",  "id":17, "ok":true,  "r":{...} }
{ "t":"res",  "id":17, "ok":false, "e":{"code":"session/busy","msg":"..."} }
{ "t":"evt",  "ch":"sess:s_123", "seq":8842, "m":"session.delta", "p":{...} }
{ "t":"ping" } / { "t":"pong" }
{ "t":"bye",  "code":"revoked" }
```

- `seq` 单调递增，**每通道独立**；断线重连带 `resume{ch, seq}`，宿主用 dsh 的 `session.follow` 从游标续播。
- 单帧上限 256 KiB；超出走二进制通道。

二进制帧（文件/终端），首字节区分：

```
[0x01][4B chId][8B offset][payload]     文件块
[0x02][4B chId][payload]                终端输入/输出
```

每个方法有 zod schema 校验入参；错误码统一（`session/busy`、`fs/escape`、`auth/expired`、`lock/locked`）。

**三个字段的语义**（这是锁屏能与路由表共存的关键）：

| 字段 | 缺省 | 含义 |
|---|---|---|
| `lockExempt` | `false` | 锁定态**仍允许**。只有 4 个方法，且都只读或只作用于锁本身 |
| `tier: 'unlocked'` | — | 只有 `unlocked` 允许；`soft-locked` 与 `locked` 都拒绝 |
| 两者都无 | — | 锁定态拒绝，`soft-locked` 允许（即"只读操作"） |

**需求 10/11 引入了这条表里最重要的一条新纪律：看结构可以，看内容要解锁。**

半锁（soft-locked）的用途是"人走了但任务还在跑，我想知道它在干什么"。所以放行的是**结构性信息**——目录树、文件名、改了哪些文件、±多少行、git 分支与提交标题、执行过程里有几步、每步成功与否、跑了多久。拒绝的是**内容**——文件正文、diff 正文、工具入参与输出、终端全量日志。

这条界线的意义不只是分级：**如果 `session.trace` 返回了工具输出，而 `fs.read` 被拒，那半锁就是假的**——攻击者只要让 agent 去 `cat ~/.ssh/id_rsa`，再读 trace 就绕过了。所以裁剪必须做到条目级（`TraceItem.redacted`），不能只做方法级。

判定的**执行点只有两处**，且职责分明：

- 方法级：`plugin/src/gateway/guard.ts`，路由表是数据，guard 是唯一实现——避免每个 handler 各写一句 `if (locked)`（这是同类插件最常见的漏洞来源）。
- 条目级：trace/diff handler 内部的 `redact()`，只作用于返回体。它不能替代方法级判定，只能在其之上更严。

详见 `06-锁屏与远程安全.md` §4.2/§4.3 与 `07-详细设计.md` §5.2。

### 3.4 多路复用与背压

- 一条 WSS 挂 N 个逻辑通道：`ctl`、`sess:<id>`、`trace:<id>`、`fs:<id>`、`term:<id>`。
- 每个通道有 credit 窗口（默认 1 MiB）；接收方 `ack{ch, consumed}` 归还额度，发送方不超发。
- 终端/流式输出按 **16ms 合批** 下发，避免手机端每 token 重渲染。
- **trace 单独走一条通道**，不和对话流挤在一起：执行过程的瞬时速率比对话高一个数量级（一轮可能 200 条 tool 事件），挤在一个通道里会把对话文字挤出背压窗口，用户看到的就是"agent 在跑但字不动了"。

### 3.5 执行过程与队列的协议语义

这两块都是"会话"的延伸，但**数据的来源完全不同**，这决定了它们的实现位置：

| | 执行过程（trace） | 消息发送队列（queue） |
|---|---|---|
| 数据来源 | dsh 的 session 事件流（只读投影） | **我们自己造的状态** |
| 为什么 | dsh 已经在产生这些事件，我们只是归一化 | dsh 一次只接受一条 prompt，没有排队概念 |
| 实现位置 | 插件侧归一化层 `plugin/src/trace/` | 插件侧内存表 + 落盘 `~/.dsh/dsh-link/queue/<sessionId>.json` |
| 重启后 | 从 dsh 重新订阅即可重建 | 必须落盘，否则用户排的 5 条消息全丢 |

**归一化的必要性**：dsh 的事件形状是内部实现，小版本升级会变。如果协议直接透传 dsh 事件，一次 dsh 升级就会让 App 白屏。所以插件侧必须有一层 `dsh event → TraceItem` 的映射，协议只认 `TraceItem`。这层映射的完整表格在 `07-详细设计.md` §5.1。

**队列的三个状态转换**（`pending → sending → sent`，异常走 `failed`）：

```
push ──► pending ──(会话空闲 & autoStart)──► sending ──► sent   （出队）
           │                                    │
           ├──(用户删除)──► canceled            └──(prompt 抛错)──► failed
           └──(用户重排)──► pending（order 变）
```

两条容易做错的：

1. **`sending` 不可编辑**。用户在消息发出去的那 200ms 里点了"编辑"，如果允许，就会出现"界面显示的是新文本、agent 收到的是旧文本"。所以 `sending` 状态一律返回 `queue/immutable`。
2. **失败不自动重试**。agent 拒绝一条 prompt 通常是因为上下文或权限问题，自动重试只会把同一个错误刷三遍。失败条目留在队列里，等用户改完再发。

## 4. 认证与安全

### 4.1 身份模型

```
Host  ── 一对长期密钥（Ed25519 签名 + X25519 交换，可复用同一 keypair）
  └─ Device（每台手机一条记录）
       ├─ deviceId   = base32(SHA256(devicePub))[0:16]
       ├─ devicePub  = 设备公钥（首次配对时登记）
       ├─ name/plat  = "iPhone 15 / iOS 18"
       ├─ role       = viewer | operator | approver | admin
       ├─ createdAt / lastSeen / revokedAt
       └─ pairSecretHash（配对时一次性，用后即焚）
```

- 设备私钥存 **iOS Keychain / Android Keystore**（uni-app 通过 uts 调原生，退化为 `plus.storage` 加密存储）。
- 宿主侧存设备公钥，**永不存私钥**；撤销即删记录，令牌立刻失效（无状态票据靠 `revokedAt` 表比对）。

### 4.2 密码的定位

dsh 本身没有账号，所以密码不是"登录密码"，而是**设备持有之外的第二因子**：

| 模式 | 行为 | 适用 |
|---|---|---|
| `new-device`（默认） | 只有新设备首次配对要输密码 | 日常最省事 |
| `always` | 每次冷启动 App 要输（或生物识别替代） | 手机可能被他人拿到 |
| `off` | 仅设备密钥 | 纯内网/Tailscale 信任环境 |

- 存储：`scrypt(password, salt, N=16384, r=8, p=1, keylen=32)`，只存 `salt`/`hash`/参数三元组；比对用 `timingSafeEqual`。
  - **为什么不用 Argon2id**：它需要 native 模块，在 Electron 打包环境里跨平台编译是长期痛点；`node:crypto` 自带 scrypt 且 `dsh-startup-moss` 已在生产验证（`lib/gate.js` 的服务端部分）。参数调到 16k 后单次约 60–80ms，对"输入密码"这个场景完全够。
- 传输：密码经 E2E 通道内的 `pwdProof = HMAC(mk, "pwd"‖password)`，**明文密码永不出现在线上**。
- 防爆破：按 `deviceId + IP` 双维度，5 次失败锁 60s，全局失败率超阈值时进入"仅允许已配对设备"模式。
- **同一个密码两处用途**：① 新设备配对（本节）② dsh 锁定态解锁（`06-锁屏与远程安全.md` §6）。落地为 `config.lock.password` 一份记录，避免用户记两个密码。
  代价是配对密码泄露即可解屏，所以配对成功后应立即引导改密码（产品流程见 `03-产品设计.md` §6.1 第 5 步）。

### 4.3 角色与权限矩阵

### 4.4 传输安全

| 场景 | 外层 | 内层 | 说明 |
|---|---|---|---|
| 局域网 | 无（明文 WS） | XChaCha20-Poly1305 | 绕开自签证书；密钥不落地 |
| Tailscale | WireGuard | 同上 | 双保险 |
| 公网中继 | TLS 1.3 | 同上 | 中继只见密文 |
| 用户自备反代 | TLS 1.3 | 同上 | 反代需支持 WS Upgrade |

> **实现状态：内层（E2E）尚未实现。** `gateway/server.ts` 建的是 `createServer`（明文 HTTP），
> `core/transport.ts` 用明文 `ws://`，`seal/open` 只有接口没有实现。所以**现在是全链路明文**，
> 「局域网明文 + 应用层加密」这个组合里的后半句还缺着。这条决定了当前版本不能上公网。
> 实现顺序也必须固定：**先 E2E，再密码校验**——反过来的话 `pwdProof` 会出现在明文里。见 `09` §5.2。

- 前向保密：每次连接生成临时 X25519，长期密钥只用于签名。
- 重放防护：帧计数器 + 64 帧滑动窗口；1 小时或 2^20 帧强制 rekey。
- 审计：`auth.ok / auth.fail / fs.write / plugin.install / device.revoke / lock.*` 写本地 JSONL（0600），App 端"安全日志"可读。

### 4.5 锁屏：三个强制点与一个做不到

锁屏不是"盖一层半透明遮罩"，它由三个互不替代的强制点组成。完整设计见 `06-锁屏与远程安全.md`，这里只给工程落点。

| 层 | 谁执行 | 强度 | 落点 |
|---|---|---|---|
| **L1 界面锁** | 客户端半 | 挡人（T1） | `client/lock-ui.js`：全屏层 + 焦点陷阱 + 键盘拦截 + 内容 `display:none` |
| **L2 远程锁** | 网关 | 挡设备（T2） | `src/gateway/guard.ts`：锁定态除 4 个 `lockExempt` 方法外一律 `lock/locked` |
| **L3 动作闸** | 网关 | 挡半锁态写操作 | 同一 guard，按 `tier: 'unlocked'` 判定 |

**做不到的那一件（必须写进产品文案）**：本机已登录浏览器的 Remote 调用拦不住。原因是 dsh 没给 owner 调用链留钩子：

```ts
// 想拦，但没有位置可拦：
ctx.connection.rpc.intercept('/api', …, …)   // ✗ 抛 "shared RPC channel "/api" already has an interceptor"
                                             //   （rpc-host.ts:293-295，Gateway 的 Host 入口已占用）
ctx.connection.requestRejection(req)         // ✗ 只读查询，返回 401|403|undefined（rpc-host.ts:123）
ctx.remoteAccess.decide(...)                 // ✗ owner 调用直接跳过（Gateway README:33）
```

所以锁屏的价值边界是：**挡人、挡远程设备，不挡本机进程**。T4 属于操作系统账号安全，不在本插件的防护范围内。

**不做什么**（避免步 moss 的后尘）：
- 不 patch `ctx.webServer.server`、不接管 `ctx.connection`（对比 `dsh-remote-mobile` 的脆性）。
- 锁定时**不暂停**正在跑的 agent。锁屏锁界面，不锁进程——这条要写在设置页，否则用户会误以为"锁了就不干活了"。

## 5. 网络与多通道

> **本章是设计，不是现状。** 截至 2026-10-23，`relayUrl` 只是配置项、没有任何代码去连中继；
> App 侧只有 `endpointKind` 一个用于显示的标签，没有 endpoint 列表也没有竞速；
> 网关绑在单个 LAN IP 上，明文 WS。
> 完整的现状盘点、局域网发现/寻址/连通的细节、稳定性分级与攻击面清单见 **`09-网络访问机制.md`**。
> **若已有 nps / frp，自研中继可以整块跳过**——用它的 TCP 隧道或域名转发挂一个目标地址即可，
> 宿主侧一行代码都不用改。代价与前提（TLS 谁终止）见 `09` §2.5。

### 5.1 endpoint 模型

```ts
type Endpoint =
  | { kind: 'lan';      url: string; prio: 100 }
  | { kind: 'tailscale';url: string; prio: 80  }
  | { kind: 'relay';    url: string; prio: 50  }
  | { kind: 'custom';   url: string; prio: 60  }
```

配对二维码里带 **全部** endpoint（LAN 可能有多个网卡），App 依次竞速：

```
并行发起前 2 个（LAN 优先），400ms 内无握手成功 → 追加 relay
首个 AuthOk 的通道胜出；其余 800ms 后关闭（避免抖动）
```

### 5.2 中继协议

```jsonc
// 主机出站连接
{ "t":"host.register", "hostId":"...", "hostPub":"...", "sig":"..." }
// App 连接
{ "t":"client.attach", "hostId":"...", "deviceId":"..." }
// 中继只做：配对两端 + 转发帧 + 通知离线
{ "t":"peer.join" | "peer.left" | "frame" }
```

- 中继**不看明文**，也**无法伪造**：Auth 帧的签名覆盖 transcript，中继改一个字节就会失败。
- 自托管：`docker run -p 8443:8443 -v ./data:/data dshlink/relay`，单实例 1 万连接约 200MB。
- 中继只保留 `hostId → 连接` 的内存映射与 30s 心跳，不落盘。

### 5.3 保活与重连

| 层 | 策略 |
|---|---|
| 心跳 | App 每 15–25s `ping`（**不是 2s**），10s 无 `pong` 判定半开，立即重建 |
| 重连 | 指数退避 0.5 → 30s（jitter ±20%）；前台重连更激进（1s 起）；**切网事件立即重连，不等退避** |
| 恢复 | `resume{ch, seq}`；宿主从 dsh `session.follow` 游标续播，App 端按 seq 去重 |
| 幂等 | 写方法带 `clientReqId`，宿主保留 5 分钟去重表——否则重连重发会让 PC 上多出一条指令 |
| iOS 后台 | 不指望长连接：退到后台 30s 后主动断开，靠本地通知 + 回前台重连 |
| 唤醒 | 可选"保持唤醒"开关（调 `caffeinate` / `powerSaveBlocker`），与 Qoder 的 Keep Awake 对齐 |

> **心跳现在配的是 2000ms（`config.ts:93`），要改。** 移动网络的无线资源控制有个约 10s 的 tail time，
> 每 2 秒一个包会让基带永远停在 connected 态，待机功耗显著上升；而 NAT 保活只需要短于映射老化时间
> （运营商 TCP 一般 300s 以上，家用路由器 30–120s）。20–25s 足够，2s 纯属自伤。
> 客户端也**还没有死线判定**——只在 `onClose` 时重连，而切基站时 TCP 可能几分钟都不发 RST，
> 表现为"显示在线、发消息 20 秒超时"。详见 `09` §4.1。

### 6.2 App 侧数据模型（SQLite）

```sql

workspace(id PK, device_id, name, path, sort)
session(id PK, device_id, workspace_id, title, status, updated_at, last_seq)

```

- 冷启动顺序：`读 device → 渲染本地缓存会话 → 起连接 → 增量对齐`。首帧不等网络。
- 消息表只留最近 2000 条/会话，更早的从宿主 `session.page` 拉。

### 6.3 设备状态机

```
offline ──(尝试连接)──> connecting ──(AuthOk)──> online
   ↑                        │                     │
   │                   (超时/拒绝)           (心跳失败)
   └──────── needs-auth <───┘                     │
   └────────────────── reconnecting <────────────┘
```

UI 上只暴露 4 个：`在线 / 连接中 / 需验证 / 离线`。**不做"检测中"的抖动**——用 400ms 去抖窗口合并。

**锁定态是正交维度，不是第五个连接状态**。`online` 之后还有一个 `lock` 子状态（`unlocked` / `soft` / `locked`），来自真正的连接内推送 `lock.changed`，而不是探测出来的：

```
online{unlocked} ──lock.changed──> online{locked} ──unlock.ok──> online{unlocked}
```

UI 表达（与 `05-视觉与动效` 的胶囊表一致）：

| 连接 | 锁 | 卡片上显示 |
|---|---|---|
| online | unlocked | `在线` + 青绿呼吸点 |
| online | locked | `已锁定` + 锁图标 + 550W 红 |
| online | soft | `只读` + 黄点 |
| offline | — | `离线` + 空心灰点（**不显示锁状态**，因为不知道） |

> 最后一行是个容易做错的地方：离线设备**不能**保留上一次的"已锁定"标签。用户会以为"它锁着所以连不上"。锁状态随连接销毁。

## 7. 文件子系统（需求 4）

### 7.1 官方能力边界（必须写进代码注释）

| 通道 | 位置 | 可写 | 用途 |
|---|---|---|---|
| `workspaceFiles.*` | 工作区/任意可读路径 | ❌ 只读 | 预览、下载 |
| `attachment-local` | `DSH_HOME/files/**` | ✅（官方内部） | 作为消息附件喂给 agent |
| **`dsh-link fs.upload`** | **工作区内** | ✅（本插件） | 真正把文件放进项目 |

### 7.2 上传流程

**只有一个方法名：`fs.upload`。** 三阶段靠请求里的 `phase` 字段区分，不拆成
`fs.begin` / `fs.chunk` / `fs.commit` 三个 RPC——拆成三个名字意味着三份 policy、
三份 guard、三次往返，而它们本来就是同一次上传的三个瞬间。

```
App: 选文件 → 算 sha256
     fs.upload{phase:'create', wsId, relPath, size, sha256}
Host: 校验 → {uploadId, offset:0}          （目标已存在同 sha256 → 直接 done，秒传）
App: 分块 512KiB 二进制帧
     fs.upload{phase:'chunk', uploadId, offset, data}
Host: 写 <root>/.dshlink-tmp/<uploadId>.part → 每 4MiB fsync
App: fs.upload{phase:'complete', uploadId}
Host: fsync → rename 到目标 → {path, bytes}
```

- **断点续传**：`phase:'create'` 时若存在同 `sha256` 的 `.part`，返回已有 `offset`。
- **配额**：单文件默认 2 GiB、单设备 10 GiB/天（可配）；超限返回 `fs/quota`。
- **注入会话**：`phase:'complete'` 带 `inject:true` 时，宿主把 `@relativePath` 作为下一条
  prompt 的引用（或走 `session.prompt` 的用户确认流程），实现"上传完直接让 agent 处理"——
  对齐 WorkBuddy 的"手机拍、电脑处理"。

> 协议里 `fs.upload` 的标记是 `binary: 'up'`（`METHODS` 的第 28 个），
> 二进制帧与 JSON 帧共用一条 WS，由帧头的类别区分，见 `07` §3.9。

### 7.3 路径安全（最容易出事的地方）

```ts
function resolveInside(root: string, rel: string): string {
  if (rel.includes('\0')) throw err('fs/escape')
  if (path.isAbsolute(rel) || /^[a-zA-Z]:/.test(rel)) throw err('fs/escape')
  if (/^\\\\/.test(rel)) throw err('fs/escape')        // UNC
  const target = path.resolve(root, rel)
  const realRoot = fs.realpathSync(root)
  // 逐段 lstat，拒绝软链逃逸
  let cur = realRoot
  for (const seg of path.relative(realRoot, target).split(path.sep)) {
    if (seg === '..') throw err('fs/escape')
    cur = path.join(cur, seg)
    const st = lstatIfExists(cur)
    if (st?.isSymbolicLink()) {
      const real = fs.realpathSync(cur)
      if (!real.startsWith(realRoot + path.sep)) throw err('fs/escape')
    }
  }
  return target
}
```

- 禁写：`.git/` 内部对象、`node_modules/`（可配置）、`.dshlink-tmp/` 自身。
- 原子落盘：必须 `rename`，绝不直接写目标路径（避免 agent 读到半个文件）。
- Windows：拒绝保留名（`CON`/`PRN`/`AUX`/`NUL`）与尾部空格/点。

### 7.4 下载与预览

- 文本：`fs.read`（分页，`offset`/`bytes`），App 端虚拟滚动。
- 小二进制（< 256 KiB，缩略图、图标）：`fs.read` 返回 base64，一次拿完。
- 大二进制（图片原图 / PDF）：走 HTTP 面的 `/dsh-link/blob?scope=&path=`，支持 `Range`，
  边下边打开。**不塞进 WS**——一张 3 MB 的照片过 WS 会卡住整条控制信道，
  而这条信道同时还在传 trace 和队列。该面沿用 `/health` 同一个 server（`gateway/server.ts`），
  鉴权复用设备票据。
- 产物清单：订阅 `session.changes`，diff 变化推到 App 的"本轮改动"卡片
  （对齐 Qoder 的 diff 预览）。

### 7.5 文件浏览（需求 11 的只读面）

这个需求几乎不用写新代码，因为 `workspaceFiles` 的只读面就是为它准备的：

| 能力 | 官方接口 | 说明 |
|---|---|---|
| 列目录 | `list(scope, path, signal)` | `scope` 是工作区 id，宿主据此做根校验 |
| 元信息 | `stat(scope, path, signal)` | 拿 size/mtime/是否目录 |
| 读内容 | `read(scope, path, signal)` / `readBytes(...)` | 文本走 `read`，二进制走 `readBytes` |
| 变更流 | `changes(...)` | 订阅式；用于"边跑边看文件变化" |

**`fs.stat` 的三项自检**（这三项决定了 App 能不能正确渲染，缺一项就会出现"打开是乱码"）：

1. **二进制判定**：读开头 `probeBytes`（默认 8 KiB），含 `\x00` 即判二进制。不做这个判断，用户点开一张 png 会看到一屏替换字符。
2. **行数**：只在 `size <= maxCountLinesBytes`（默认 4 MiB）时统计，否则返回 `0` 并在 UI 上不显示"共 N 行"。为一个大文件数行数会阻塞宿主事件循环。
3. **`tracked`**：判断该文件是否在 git 索引里（`git ls-files --error-unmatch`）。App 据此决定"历史"按钮是否出现——对未跟踪的文件显示历史入口，点进去只会得到空列表。

**分页而不是全量**：`fs.read` 默认返回 `maxReadBytes`（256 KiB）一页，`offset` 续读。手机上一次读 2 MB 文本会直接把 WebView 卡住，而这个 App 的卖点之一就是"能看文件"。

`fs.read` 属于**内容类**，半锁时拒绝（§3.3 的分级纪律）。`fs.list` / `fs.stat` 属于结构类，半锁放行——这样"人走了，我想看看它产出在哪个目录"仍然可用。

### 7.6 git 与仓库浏览（需求 11 的后半）

**只读，且只读子命令白名单。** 这是本节唯一的硬约束：

```ts
// plugin/src/repo/git.ts —— 允许的子命令是一个字面量联合，不是字符串拼接
const READONLY_SUBCOMMANDS = ['status', 'diff', 'log', 'show', 'branch', 'ls-files', 'rev-parse'] as const
type GitCmd = (typeof READONLY_SUBCOMMANDS)[number]

export async function git(root: string, cmd: GitCmd, args: readonly string[]): Promise<string> {
  // 三条防线，缺一不可：
  //   1. cmd 来自白名单联合类型，编译期就挡住 'push'
  //   2. args 逐项校验：不许以 '-' 开头之外的自由文本（防 `-c core.pager=...`）
  //   3. 用 `--` 分隔路径，防路径被解释成选项
  const safeArgs = args.filter((a) => !a.startsWith('-c') && !a.startsWith('--exec'))
  return execFile('git', ['-C', root, cmd, ...safeArgs, '--'], { timeout: 8000, maxBuffer: 512 * 1024 })
}
```

用 `execFile` 而不是 `exec`：不经过 shell，就不存在注入面。这是唯一正确的选择，`exec` + 字符串拼接在这里等于把 RCE 送人。

**仓库发现的三种情况**（对应 `RepoSummary.kind`）：

| kind | 判定方式 | 能否看历史 |
|---|---|---|
| `workspace` | 工作区根本身有 `.git`（`git rev-parse --show-toplevel` 等于工作区路径） | ✅ |
| `nested` | 工作区某个子目录有 `.git`（扫描深度 2 层，跳过 `node_modules`） | ✅ |
| `github` | 没有本地 clone，靠 `repo.gh.*` 走 GitHub REST | ✅（远程 API） |

**`repo.list` 的默认边界**：只扫工作区内部。`repo.allowOutsideWorkspace` 默认 `false`——"顺带浏览我整个家目录的仓库"是明确的权限放大，需要用户显式打开。

**GitHub 远程浏览（M3）的安全要点**：

1. **token 只存在 PC 上**（`config.repo.github.token`），绝不下发、绝不进审计日志、绝不出现在错误 message 里（常见事故：把带 token 的 URL 打进异常栈）。
2. **默认关闭**（`caps.gh = 0`）。App 拿到 `gh: 0` 就不显示远程仓库入口，而不是点进去才报错。
3. **allowlist**：为空表示不限制，非空则只允许列表内的 `owner/repo`。
4. **限流要透传**：GitHub 返回 `403` + `X-RateLimit-Reset` 时，转成 `repo/auth` 或带 `retryAfterMs` 的错误，让 App 能显示"还差 12 分钟"而不是一个笼统的失败。

## 8. 插件子系统（需求 6）

### 8.1 远端：把 dsh 的插件管理搬到手机

`pluginManager` 的 12 个 `@Remote` 方法几乎是为这个需求量身定做的：

| App 操作 | 调用 | 反馈 |
|---|---|---|
| 打开插件页 | `listBundles()` + `listPlugins()` | 卡片列表（含 `official/optional/installed/availability`） |
| 搜索/预览包 | `inspect(spec)` | name/version/description/是否 bundle/registry/problem |
| 安装 | `installBundle(spec,{requestId,enabled:true})` | 订阅 `plugin-manager/install-state`（installing/cancelling/applying）+ `install-log` 流 |
| 取消 | `cancelInstall(requestId)` | `cancelled / too-late / not-running` |
| 恢复丢失响应 | `waitForInstall(requestId)` | 同原结果 |
| 启用/禁用 | `setBundleEnabled(name, on)` / `setPluginEnabled(id, on)` | `plugin-manager/changed` |
| 卸载 | `removeBundle(name)` | 同上 |
| 版本豁免 | `listVersionExemptions / setVersionExemption` | 兼容旧 dsh 的逃生口 |

三条工程注意：

1. `installBundle` 有 `pendingBuilds`（pnpm 11 拦构建脚本）→ App 必须能展示"这些包要跑安装脚本"并二次确认（`approvedBuilds`）。
2. `restart-required` 是常态（`no-hmr` / `package-moved`）→ App 要提供"重启 dsh"按钮（宿主侧 `app.relaunch`）。
3. 安装是**长时间操作**（几十秒到几分钟）→ 必须可后台化 + 通知，不能卡在 loading 转圈。

### 8.3 App 端：一个"参考 dsh"的插件机制

uni-app 不能动态加载原生代码，所以照搬 dsh 的双半架构要降级成**两档 surface + 一套 manifest**：

```jsonc
// manifest.json（宿主下发或本地安装）
{
  "id": "com.dshlink.monitor",
  "name": "机器监控",
  "version": "1.2.0",
  "apiVersion": 1,
  "icon": "builtin:cpu",
  "surfaces": [
    { "type": "declarative", "slot": "device.detail",
      "schema": { "type": "grid", "cols": 2, "items": [
        { "type": "stat", "label": "CPU", "source": "action:cpu" },
        { "type": "stat", "label": "内存", "source": "action:mem" }
      ]}},
    { "type": "webview", "slot": "device.tab", "title": "酒馆",
      "entry": "https://host.local/ext/tavern/index.html", "permissions": ["host.fetch"] }
  ],
  "actions": [
    { "id": "cpu", "kind": "host.call", "target": "ext:monitor.cpu", "schema": {} }
  ],
  "permissions": ["device.info"]
}
```

- **declarative**：JSON → 原生组件（`stat/grid/list/kv/progress/chart/action`），安全、快、离线可用。
- **webview**：`<web-view>` 承载，通过 `uni.postMessage` 与原生桥通信；能力受 `permissions` 白名单约束。
- **host.call**：宿主侧执行（等价于 dsh-mobile 的 `api.host.invoke`），一个动作一个白名单。
- 分发：① 由电脑端决定（`GET /v1/appext`，PC 装了什么，手机就看到什么）；② 扫码装（manifest URL + 签名）。

这套设计对齐 dsh 的三个关键语义：**manifest ≈ cordis.patch.yml、actions ≈ host 半、surfaces ≈ client 半**，并且**不可信代码永远在 webview 里**。

### 8.4 与 dsh-mobile 的集成（需求 7）

| dsh-mobile 能力 | 我们的处理 | 复用方式 |
|---|---|---|
| 配对（扫码/链接/密钥） | 协议兼容层 | 识别 `dsh-mobile://pair` 链接，转成我们的配对 |

### 9.2 路由分发（含角色 + 锁屏校验）

```ts
// plugin/src/gateway/router.ts
export function makeRouter(ctx: Context, cfg: Config, store: DeviceStore) {
  return async function dispatch(sess: Session, m: string, p: any) {
    const route = ROUTES[m]
    if (!route) throw rpcError('rpc/unknown')

    // ① 锁：唯一执行点，见 06 文档 §4
    guardLock(readLockState(ctx), route, m)

    // ② 角色
    if (!hasRole(sess.role, route.role)) throw rpcError('auth/forbidden')

    if (route.stream) return route.stream(ctx, p, sess.signal)
    return route.fn(ctx, p, sess)
  }
}

// plugin/src/gateway/guard.ts
export function guardLock(lock: LockState, route: Route, method: string): void {
  if (route.lockExempt) return                 // 4 个豁免方法：解锁与看状态
  if (lock.locked) {
    throw new RpcError('lock/locked', 'host is locked', { since: lock.since, reason: lock.reason })
  }
  if (lock.soft && route.tier === 'unlocked') {
    throw new RpcError('lock/readonly', 'host is in read-only mode', { since: lock.since })
  }
}
```

### 9.3 锁屏状态机（宿主半）

```ts
// plugin/src/lock/index.ts
export interface LockState {
  readonly locked: boolean
  readonly soft: boolean
  readonly since?: number
  readonly reason?: 'idle' | 'manual' | 'remote' | 'boot'
  readonly failedAttempts: number
}

export function createLock(ctx: Context, cfg: LockConfig) {
  let state: LockState = { locked: false, soft: false, failedAttempts: 0 }
  let timer: ReturnType<typeof setTimeout> | undefined

  const publish = () => {
    ctx.set('dshLinkLock', state)                       // 供网关软读
    broadcast('lock.changed', state)                    // 推给所有在线设备
    ctx.emit('dsh-link/lock-changed', state)            // 供客户端半订阅
  }

  const idleTimer = () => {
    if (timer) clearTimeout(timer)
    if (!cfg.idleMinutes) return
    timer = setTimeout(() => lock('idle'), cfg.idleMinutes * 60_000)
  }

  function lock(reason: LockState['reason']) {
    if (state.locked) return
    state = { ...state, locked: true, since: Date.now(), reason }
    audit({ ev: 'lock', reason })
    publish(); resetCredentialsTier()                   // 设备角色临时降为 viewer
  }

  function unlock(password: string): string {
    if (!verifyScrypt(cfg.password, password)) {        // 服务端比对，浏览器永不见 hash
      state = { ...state, failedAttempts: state.failedAttempts + 1 }
      audit({ ev: 'unlock.fail', attempt: state.failedAttempts })
      publish()
      throw new RpcError('lock/bad-password', 'wrong password', { attempt: state.failedAttempts })
    }
    state = { locked: false, soft: false, failedAttempts: 0 }
    audit({ ev: 'unlock.ok' })
    publish(); idleTimer()
    return issueTicket(cfg, 12 * 3600_000)              // HMAC 票据
  }

  idleTimer()
  return { get: () => state, lock, unlock, touch: idleTimer }
}
```

### 9.4.1 执行过程：归一化层

这一层是需求 10 的核心，也是最容易被低估的一段代码。它的工作只有一件事：**把 dsh 的内部事件翻译成 `TraceItem`，并且保证翻译失败时不炸**。

```ts
// plugin/src/trace/normalize.ts
import type { TraceItem } from '@dsh-link/protocol'

/**
 * dsh event → TraceItem。
 *
 * 三条纪律：
 *  1. 认不出的事件返回 undefined 而不是抛错。dsh 加新事件类型是常态，
 *     我们不能因为它加了个 'context-compacted' 就让整个 trace 流崩掉。
 *  2. seq 由我们自己发，不用 dsh 的字段。dsh 的事件序号语义没写进文档，
 *     依赖它等于依赖实现细节。我们用一个会话内的单调计数器。
 *  3. 大字段一律截断（input/output/tail），完整内容存 ring buffer 里，
 *     trace.detail 按 seq 取。协议帧不能因为一条 `npm install` 的日志就超 256 KiB。
 */
export function normalize(ev: DshSessionEvent, seq: number): TraceItem | undefined {
  switch (ev.type) {
    case 'assistant-thinking':
      return { k: 'think', seq, at: ev.at, summary: clip(ev.summary, 300) }

    case 'assistant-text':
      return { k: 'text', seq, at: ev.at, text: ev.delta ?? ev.text, streaming: ev.partial }

    case 'tool-call':
      return {
        k: 'tool', seq, at: ev.at,
        tool: ev.name,
        target: ev.input?.path ?? ev.input?.pattern,
        input: clip(JSON.stringify(ev.input), 200),
        output: clip(ev.result?.text, 400),
        ms: ev.durationMs,
        ok: ev.ok,
      }

    case 'file-changed':
      return { k: 'file', seq, at: ev.at, path: ev.path, op: ev.op,
               additions: ev.additions, deletions: ev.deletions, from: ev.from }

    case 'terminal':
      return { k: 'term', seq, at: ev.at, cmd: clip(ev.cmd, 200), exit: ev.exitCode,
               tail: tailLines(ev.output, cfg.trace.maxTailLines) }

    case 'approval-request':
      return { k: 'approval', seq, at: ev.at, id: ev.id, cmd: ev.command, risk: ev.risk }

    case 'question':
      return { k: 'question', seq, at: ev.at, id: ev.id, q: ev.question,
               options: ev.options, multi: ev.multiSelect }

    case 'error':
      return { k: 'error', seq, at: ev.at, code: ev.code, msg: clip(ev.message, 300) }

    default:
      return undefined   // 认不出就丢，不要让新事件类型打穿协议
  }
}
```

**`redact()` 是它的兄弟函数**，也是半锁能成立的关键：

```ts
// plugin/src/trace/redact.ts
/**
 * 只读半锁下的裁剪：保留"做了什么"，清掉"内容是什么"。
 *
 * 为什么必须做在条目级：如果只做方法级（拒绝整个 session.trace），
 * 用户就完全不知道 agent 在干什么，半锁也就失去了唯一的用途；
 * 如果什么都不做，攻击者可以让 agent `cat ~/.ssh/id_rsa` 再读 trace，
 * 从而绕过 fs.read 的内容限制。所以裁剪的粒度必须细到条目字段。
 */
export function redact(item: TraceItem): TraceItem {
  switch (item.k) {
    case 'text':  return { ...item, text: '', redacted: true }
    case 'tool':  return { ...item, input: undefined, output: undefined, redacted: true }
    case 'term':  return { ...item, tail: undefined, redacted: true }
    case 'think': return { ...item, summary: '', redacted: true }
    default:      return item   // file / approval / question / error 只有结构，无需裁剪
  }
}
```

注意 `file` 条目**故意不裁剪**：它的 `path` + `additions/deletions` 恰恰是半锁最想给用户看的东西（"它在改这个文件，加了 42 行"）。而路径本身不是秘密——`fs.list` 在半锁下本来就允许。

### 9.4.2 消息队列：状态机与落盘

```ts
// plugin/src/queue/index.ts
/**
 * 消息发送队列。
 *
 * 为什么在插件侧而不是 App 侧：队列必须以"宿主收到了什么"为准。
 * 如果队列在 App 里，用户在两台手机上各排三条，就会互相不知道对方的存在；
 * 而且 App 被杀掉之后队列就没了。放在宿主，多端看到的是同一份队列。
 */
export class SendQueue {
  #items: QueueItem[] = []          // 内存快照，顺序即 order

  /** 落盘：~/.dsh/dsh-link/queue/<sessionId>.json，只在 pending 变化时写，不做每帧写 */
  async #persist(): Promise<void> { /* 原子写：tmp + rename */ }

  push(text: string, attachmentCount = 0): QueueItem {
    if (this.#items.filter((i) => i.state === 'pending').length >= cfg.queue.maxItems)
      throw new RpcError('queue/full', `队列已满（${cfg.queue.maxItems} 条）`)
    const it = { id: newId(), sessionId, text, attachmentCount, createdAt: Date.now(),
                 state: 'pending' as const, order: this.#items.length }
    this.#items.push(it); void this.#persist()
    return it
  }

  /** 会话空闲时由 sessionController 的 idle 事件驱动 */
  async drain(): Promise<void> {
    const head = this.#items.find((i) => i.state === 'pending')
    if (!head) return
    head.state = 'sending'                       // 先置位再发送：防止重入
    try {
      await sessionController.prompt({ sessionId, text: head.text })
      head.state = 'sent'
    } catch (e) {
      head.state = 'failed'
      head.error = (e as Error).message          // 不自动重试，见 02 §3.5
    }
    void this.#persist()
  }
}
```

两处刻意的设计：

1. **`sending` 先置位再 await**。否则 `drain()` 被 idle 事件并发调用两次，同一条消息会发两遍。这是队列类代码最经典的 bug。
2. **`failed` 保留在队列里**，不自动重试也不静默丢弃。用户能看到"这条失败了，原因是 X"，改完再发。

| 视觉 | 灰度分层测试、60fps 采样、首包 < 400KB、色盲可辨（见 05 §8） |

## 13. 风险登记（技术侧）

| 风险 | 影响 | 触发概率 | 对策 |
|---|---|---|---|
| uni-app 自定义 TLS/证书校验受限 | 局域网 https 不可用 | 高 | 已定：LAN 走明文 WS + 应用层 E2E |
| iOS 后台长连接被挂起 | 收不到"跑完了" | 高 | 推送 + 回前台补拉；明示用户 |
| dsh 小版本改 `@Remote` 签名 | 调用失败 | 中 | 契约测试 + 能力探测 + 版本矩阵 |
| `pluginManager` 安装耗时不可控 | App 卡住 | 中 | 后台化 + 日志流 + 通知 |
| 工作区在多设备同时写 | 文件冲突 | 中 | 上传前查 mtime/冲突改名 `name (2).ext` |
| 中继被滥用 | 带宽/合规 | 低 | 需 hostId 公钥注册、单 IP 限速、可关 |
| **锁屏把自己锁在外面** | 用户无法使用 dsh | 中 | 恢复码 + 编辑 config 关闭 + 启动 90s 宽限 + 脚本崩溃自动摘罩（06 §10 六条逃生口） |
| **锁屏给人虚假的安全感** | 用户在公共场合放心离开，实际接口仍可达 | 中 | 文案明确"挡人不挡进程"；威胁模型写进设置页的展开说明（06 §3） |
| 双皮肤导致样式分叉 | 维护成本翻倍 | 中 | 只换 CSS 变量，不写分支样式；组件里禁止出现硬编码色值（05 §7） |
| **误把"锁屏"做成操作系统锁屏** | 要系统权限、不可移植、与用户预期冲突 | 中（认知风险） | 06 §0.1 把语义钉死在文档第一屏；代码里不出现任何 OS 锁屏 API；文案写「dsh 锁屏」不写「锁屏」 |
| **trace 归一化跟不上 dsh 升级** | 执行过程页空白或错乱 | 高 | 认不出的事件返回 `undefined` 丢弃；契约测试对 5 种核心事件做快照；不做"未知事件就抛错" |
| **trace 载荷过大撑爆帧** | 单帧超 256 KiB 被拒，整条流断 | 中 | 归一化时截断（input 200 / output 400 / tail 40 行）；完整内容只进 ring buffer，按需 `trace.detail` |
| **半锁被 trace 绕过** | 只读模式下仍能看到文件内容 | 中 | 条目级 `redact()`；协议测试锁住"半锁拒绝内容类方法"（`tests/frame.test.mjs` 已有 7 项） |
| **队列并发重入导致重复发送** | 同一条消息发两遍，agent 白跑一轮 | 中 | `sending` 先置位再 await；`drain()` 单飞；测试用假 prompt 校验调用次数 |
| **git 子命令被注入** | 远程 RCE | 中 | `execFile` 不走 shell + 字面量联合白名单 + `--` 分隔路径；禁止 `-c`/`--exec*` |
| **GitHub token 泄漏** | 仓库被读、账号被封 | 中 | token 只在宿主内存；错误 message 里脱敏；审计日志不记录；`caps.gh=0` 时整条路径不可达 |
