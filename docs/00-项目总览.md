## 十分钟上手

协议与插件各自装依赖、各自构建，互不干扰；移动端在独立工程里：

```bash
# ① 共享协议（先编，插件依赖它的 dist）
cd shared/protocol && npm install && npm test      # 24 passed

# ② PC 端插件
cd ../../plugin && npm install && npm test         # 10 passed
cd .. && DSH="/Applications/DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh"
"$DSH" plugin --profile desktop add "dsh-link@link:$PWD/plugin"

# ③ 移动端（独立工程 ../moss-ai-app，协议包内嵌）
cd ../moss-ai-app && npm install
npm run typecheck                                   # vue-tsc，0 error
npm run build:h5                                    # 产物 dist/build/h5，280KB
npm run dev:h5                                      # 开发预览
```

> 上面四条命令都在本机跑通过（2026-10-23；迁移后 2026-10-24 复验）：协议 24 passed、插件 10 passed、
> 类型检查 0 error、H5 构建成功、总体积 280KB（预算 400KB）。
>
> `shared/protocol` 是**源码依赖**：插件通过 `file:../shared/protocol` 引用它的 `dist/`。
> 改了协议要 `cd shared/protocol && npm run build`，否则插件侧的类型与实现会对不上
> ——这是不用 workspace 换来的唯一代价。移动端侧现在用的是 `moss-ai-app/protocol/` 内嵌副本
> （vite alias 直接引 `src/`），协议改动要**双侧同步**，见 [14-工程结构变更-app迁出.md](14-工程结构变更-app迁出.md)。
>
> 插件不 patch dsh 内部：只注册自己的路由与 WSS 网关，服务通过 `ctx.get(name, false)` 软读取。

## 一句话结论

技术上可行，架构上应选**旁路网关**（不 patch dsh 内部），
产品上守住五条红线：**配对要短、多机状态要稳、上传要安全、装插件要设权限闸、锁屏别把主人锁在外面**。

## 三条最容易踩的坑（来自前序代码级分析）

1. **cordis 4 严格代理**：插件里 `ctx.foo` 读未声明的服务会直接抛错，可选服务必须 `ctx.get(name, false)`。
2. **`/api` channel 只允许一个 interceptor**：想拦 Remote 调用会被 Gateway 占位，锁屏因此只能做「界面锁 + 网关锁」，不能做「本机 owner 的接口锁」（详见 06 文档 §3）。
3. **`requestRejection()` 是只读查询不是钩子**：它返回 `401 | 403 | undefined`，插件无法在其内部加判断。
