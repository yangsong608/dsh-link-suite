# MOSS Link · 产品设计（v2 · 基于竞品实测）

> **本文与 v1 的区别**：v1 是"自己想的应该有什么"。
> v2 的每条设计决策都能追溯到**实际看到的竞品行为**或**dsh 的真实 API 能力**，
> 并在每节末尾标注证据来源。看不到证据的条目，标 `【待验证】`。

## 0. 调研结论先说（决定整个产品形态）

### 0.1 Qoder Mobile：手机是"审批台"，不是"缩小版 IDE"

官方描述（[qoder.com/zh/mobile](https://qoder.com/zh/mobile)）：

> 随时用手机查看 Agent 进度、处理关键审批并追加指令，任务完成后直接预览并验收成果
>
> 远程控制模式下，电脑端会话**持续运行**，App **实时同步状态**，你可以随时查看进度、审批操作、回答提问、追加指令。

四个明确的能力：

| 能力 | 原话 |
|---|---|
| 看进度 | 「实时同步状态」「Agent 进度一手掌握」 |
| 处理审批 | 「Agent 需要审批、补充回答时，立即**推送通知**」 |
| 追加指令 | 「追问」「追加指令」 |
| 验收成果 | 「任务产物与代码 **Diff** 都能直接在手机上查看」 |

**关键洞察**：它把"看"和"动手"分得很清。手机不做代码编辑，只做
**判断**（批复/拒绝）和**追加**（说一句话）。这是手机物理条件决定的。

### 0.2 WorkBuddy：三段式信息架构 + 明确的分组

官方文档（[WorkBuddy 简介](https://www.workbuddy.cn/docs/workbuddy/Overview)）给出四区布局：

| 区域 | 功能 |
|---|---|
| 工具栏 | 顶部常用操作 |
| 侧边栏 | **任务列表（按文件夹分组）**，支持搜索和管理 |
| 对话区 | 任务标题栏、消息列表、输入框 |
| 结果区 | 右侧面板：概览 / 产物两类，同区切换 |

**关键洞察 1**：「任务列表按文件夹分组」——这正是我们缺的**按工作区分组**。
它的分组单位是"文件夹"，我们对应的是 dsh 的 workspace。

**关键洞察 2**：结果区与对话区**并列**，不是叠在对话流里。
手机上叠放会打断阅读；并列在平板上可行，手机上应是"切换"。

远程遥控实践（[Practice-Six](https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Practice-Cases/Practice-Six)）给的用法建议：

> - **先给清晰目标**：远程场景下应避免模糊指令
> - **减少高风险操作**：涉及删除、覆盖、批量移动时，**建议先要求预览**
> - **保留关键文件名**

**关键洞察 3**：「先预览再执行」是远程场景的硬需求，不是可选功能。
在电脑前可以后悔，在手机上误操作的代价更高。

### 0.3 dsh-mobile：**不存在**

我在本机做了三次检查：

```bash
# DSH 应用内
find /Applications/DeepSeek\ Harness.app/Contents/Resources/app.asar/dsh/node_modules -maxdepth 1 -iname "*mobile*"
# → 无结果

# profile
find ~/.dsh/profiles -maxdepth 3 -iname "*mobile*"
# → 无结果

# 工作区
find . -maxdepth 2 -iname "*mobile*" -not -path "*/node_modules/*"
# → 无结果
```

**结论**：`docs/01` 里写的"技术参照 dsh-mobile 等 5 个已落地插件"是**未经核实的假设**。
v2 不再引用它，改为直接读 dsh 的真实 API 契约。

## 1. 产品定位（修正）

### 1.1 一句话

**不在电脑前时，用手机接管 dsh 的"判断"与"追加"，而不是把 IDE 塞进手机。**

与 v1 的差别：v1 说"管理并使用多台电脑上的 dsh"，太宽——"使用"暗示了什么都能做。
实际能做好的是三件事：**知道在发生什么、做决定、说下一句**。

### 1.2 三类用户与对应的核心动作

| 用户 | 场景 | 核心动作 | 屏幕 |
|---|---|---|---|
| 通勤中的开发者 | agent 跑到一半要去开会 | 看进度 → 审批 → 追加指令 | 会话详情 |
| 有多台机器的人 | 书房跑任务，卧室想知道 | 切设备 → 看哪台在忙 | 设备页 |
| 交付验收的人 | 让 agent 做完，自己验收 | 看产物 / diff → 接受或打回 | 产物页 |

### 1.3 明确不做（v2 新增的负向清单）

| 不做 | 理由（证据） |
|---|---|
| 手机端代码编辑 | Qoder Mobile 不做；手机键盘不适合改代码 |
| 完整的文件管理器 | WorkBuddy 的文件浏览在桌面侧栏，手机端只做"看产物" |
| 数据库/终端 | 输入成本与误操作风险都过高 |
| 会话物理删除 | dsh 只提供 archive（见 §3.3） |

## 2. 信息架构（按 WorkBuddy 的分组原则重排）

### 2.1 导航结构

```
┌─ 底部 3 Tab ────────────────────────────┐
│  设备        会话        我的            │
└─────────────────────────────────────────┘

设备页（P1）
└─ 设备卡列表
   └─ 点 → 会话页（该设备）
        └─ 长按 → 重命名 / 查看详情 / 断开 / 移除

会话页（P2）
└─ 按工作区分组的会话列表          ← WorkBuddy 侧边栏「按文件夹分组」
   ├─ ▸ 工作区 A（3）
   │    ├─ 等待你（2）
   │    ├─ 进行中（1）
   │    └─ 最近（5）
   ├─ ▸ 工作区 B（1）
   └─ ▸ 已归档（折叠，默认收起）    ← dsh 的 archive 语义，见 §3.3
   └─ 长按会话 → 重命名 / 归档

对话页（P3）
├─ 顶栏：工作区名 › 会话标题 · 状态
├─ 三段切换：对话 / 执行过程 / 产物   ← Qoder「看进度 + 验收成果」
├─ 消息流（含历史，见 §3.2）
└─ 输入区：文本框 + 发送 + 队列
```

### 2.2 为什么"按工作区分组"必须做

WorkBuddy 的侧边栏是"任务列表（按文件夹分组）"，因为：

- 用户对任务的记忆是**按项目**的（"那个报表的任务"），不是按时间
- 时间倒序会把"昨天的工作区 A"和"今天的 B"混在一起

dsh 的 `workspace.list` 直接给了这个维度，不用就是浪费。

## 3. 关键流程（修正过的）

### 3.1 配对（当前实现已验证可用）

```
电脑：设置 → MOSS Link → 生成配对码
      ↓ 二维码（含 ws 地址 + 6 位码）
手机：添加电脑 → 扫码
      ↓ 自动填地址与码 → pair.finish
      ↓ 电脑面板若有「等待确认」则批准
      ↓ 拿到 token，存本地
```

**证据**：这条链路已实测跑通（会话记录：`pair.start → pending → approve → finish` 全绿）。

### 3.2 进入会话：必须拉历史（当前缺失）

**这是当前最大的功能缺陷**：点进会话只有空输入框，没有历史。

dsh 的真实契约（`packages/api/session-controller/src/types.ts`）：

```ts
// 拉历史要用 page，不是 follow
interface SessionPageRequest {
  address: SessionAddress        // { kind: 'session', sessionId }
  throughSeq: number             // 从 follow 的开场帧拿到
  beforeSeq?: number             // 向上翻页
  maxMessages?: number
}

// follow 只推新事件，且开场会给一个 snapshot（含 cursor 与 hasMore）
type SessionFollowFrame =
  | { type: 'snapshot'; header; cursor; records; hasMore; projections; ... }
  | SessionEventEntry
  | { type: 'assistant-stream'; frame }
```

**正确的加载顺序**：

```
① 先 follow（拿 snapshot：历史基线 + cursor + hasMore）
② 若 hasMore → 用 page({ throughSeq: cursor, beforeSeq }) 向上补
③ follow 持续推新事件，追加到同一列表
```

**我之前的实现**只做了 ① 的一半（订阅了事件，但丢弃了 snapshot 里的 records），
所以历史是空的。这不是"没做"，是"做错"。

### 3.3 会话归档 vs 删除

dsh 只有 `workspaceController.archiveSession`，没有 delete。

| 操作 | 语义 | UI 措辞 |
|---|---|---|
| 归档 | 移出列表、日志保留 | 「归档（不再显示，记录保留）」 |
| 恢复 | 重新出现 | 「取消归档」 |

**UI 上不出现"删除"字样**——那会让用户以为数据被清掉。

### 3.4 远程场景的"先预览"（WorkBuddy 的建议）

WorkBuddy 的远程实践明确建议"涉及删除、覆盖、批量移动时先要求预览"。

落到我们这里：

| 动作 | 需要预览吗 |
|---|---|
| 批准工具调用 | **是**。显示工具名 + 参数摘要 + 影响范围 |
| 归档会话 | 是（弹确认，说明日志仍保留） |
| 撤销设备 | 是（说明该设备需重新配对） |
| 发送指令 | 否（但显示将发到哪个会话） |

## 4. 页面规格（逐屏）

### 4.1 P1 设备页

**设备卡必须显示的字段**（当前只显示了名字，这是缺陷）：

| 字段 | 来源 | 缺失时的降级 |
|---|---|---|
| 设备名 | `device.list[].label` | 「未命名设备」 |
| 平台图标 | `platform` | 通用图标 |
| 角色 | `role` | 不显示 |
| 在线状态 | 连接状态（客户端自己维护） | 「检测中」 |
| 锁状态 | `lock.locked` / `soft` | 不显示 |
| 运行中会话数 | `device.info` 里补，或从 session.list 聚合 | 不显示 |
| 连接方式 | endpoint.kind（lan/relay/tailscale） | 不显示 |
| 最近活跃 | `lastSeen` | 不显示 |

**交互**（照 `08` §3.1 的原设计补全）：

| 手势 | 行为 |
|---|---|
| 点卡片 | 未锁 → 会话页；已锁 → 请求解锁抽屉 |
| **长按 500ms** | 菜单：重命名 / 查看详情 / 断开连接 / 移除设备 |
| 下拉 | 刷新 |

**空态**：
```
还没有配对的电脑
在电脑上打开 DSH → 设置 → MOSS Link → 生成配对码
```

### 4.2 P2 会话页

```
┌──────────────────────────────────┐
│  会话                  [MOSS角标] │
├──────────────────────────────────┤
│  ▾ 工作区 A                    3  │
│    ⚠ 等待你                    2  │  ← 黄色左边线
│      · 重构上传通道...   14:05    │
│      · 分析构建耗时      13:41    │
│    ▶ 进行中                    1  │  ← 绿色脉冲点
│      · 把 auth 换成...   进行中   │
│    · 最近                      5  │
│  ▸ 工作区 B                    1  │
│  ▸ 已归档（12）          折叠     │  ← 默认收起
└──────────────────────────────────┘
```

**分组优先级**（WorkBuddy 的"按需要你的程度"+"按文件夹"合并）：

1. 同一工作区内：等待你 > 进行中 > 最近
2. 工作区之间：有"等待你"的排前，其次按最近活动

**长按会话** → 重命名 / 归档。

### 4.3 P3 对话页（信息最密）

```
┌──────────────────────────────────┐
│ ‹ 工作区A › 重构上传通道   ●运行中 │  ← 标题 + 状态
├──────────────────────────────────┤
│  对话 │ 执行过程 │ 产物           │  ← 三段切换（Qoder 的"看进度+验收"）
├──────────────────────────────────┤
│  你  14:01                        │
│  上传通道现在是整文件一次性传...     │
│                                   │
│  agent  14:01                     │
│  先看一下现在的实现...             │
│                                   │
│  ▸ Read upload.ts        42ms     │  ← 工具调用折叠成一行
│  ▸ Grep CHUNK_BYTES      18ms     │
│                                   │
│  ┌ 需要批准 ─────────────────┐    │  ← 远程审批（Qoder 核心场景）
│  │ 写入 dist/ 3 个文件 (+1.2MB)│   │
│  │ [拒绝]        [允许一次]    │    │
│  └───────────────────────────┘    │
├──────────────────────────────────┤
│ [+ 附件]  说点什么…        [发送]  │
│ 队列中 2 条 ▾                      │
└──────────────────────────────────┘
```

**必须修的三处**（当前都是缺陷）：

| 缺陷 | 现状 | 应为 |
|---|---|---|
| 无历史 | 进入只显示输入框 | 先拉 snapshot + page |
| 无头部状态 | 只有标题 | 状态点（运行中/等待/完成）|
| 输入框只有输入 | 无队列、无附件 | 队列指示 + 附件（M2）|

## 5. 状态模型（三层，照 `01` §145 的结论）

Qoder 与 WorkBuddy 都用**统一账号**把多机状态变简单（登录即绑定，绿点即在线）。
我们没有账号，所以必须自己维护状态，且要**诚实**：

| 层 | 真值来源 | 不能做的猜测 |
|---|---|---|
| 设备级 | 网关 WebSocket 握手成功 = 在线 | 不用 ICMP ping，不猜"可能在线" |
| 会话级 | `session.list[].running` | 不从"最近有消息"推断正在跑 |
| 轮次级 | `session/event` 的 turn/start、turn/end | 不按时长估算 |

**状态过期**：连接断开后显示「检测中」而不是立刻「离线」，
避免网络抖动导致列表反复跳变（`01` §148 提到的 dsh-mobile 做法，虽未验证但原则正确）。

## 6. 与 v1 的差异汇总

| 项 | v1 | v2 | 依据 |
|---|---|---|---|
| 定位 | 管理并使用多台 dsh | 接管判断与追加，不做移动 IDE | Qoder Mobile 的能力边界 |
| 会话组织 | 时间倒序 | **按工作区分组**，组内按紧迫度 | WorkBuddy 侧边栏 |
| 对话页 | 对话/执行过程/产物 三段 | 保留三段，**补历史加载** | dsh 的 page/follow 契约 |
| 设备卡 | 只显示名字 | **7 个字段** + 长按管理菜单 | `08` §3.1 原设计 |
| 会话管理 | 改名/归档 | 保留，**UI 不出现"删除"** | dsh 只有 archive |
| 远程动作 | 直接执行 | **高风险动作先预览** | WorkBuddy 实践建议 |
| 状态模型 | 三层（已写） | 保留，强调"不猜" | 无账号场景的必然 |

## 7. 待验证清单（诚实标注）

| 项 | 为什么不确定 | 怎么验 |
|---|---|---|
| dsh 能否返回多个 workspace | 本机只有一个 | 在有多工作区的机器上跑 `workspace.list` |
| `session.page` 的 `throughSeq` 从哪来 | 需读 follow 的 snapshot 帧 | 实测 follow 首帧结构 |
| 设备卡"运行中会话数"从哪取 | `device.list` 不含 | 需在 `device.info` 里补，或客户端聚合 |
| iOS 后台推送 | 需 APNs 或 Live Activity | 未开始 |
